# 資料作成キット: スライド（PowerPoint）を作る流れ

[← README.md](../README.md)

このリポジトリの skill を組み合わせて、PowerPoint の資料を「構成を決める → 作る → 点検して直す」の順で作るための手引きです。この文書だけで、流れ・点数の決め方・他のプロジェクトへの入れ方が分かるように書いています。

## 1. 目的

AI に資料を作らせると、見た目は整っていても「何を言いたいスライドか分からない」「強調している場所と主張がずれている」「日本語が不自然」といった問題が残りがちです。このキットは、次の 2 点でそれを防ぎます。

- 作る前に、聞き手・結論・各スライドの主張を決めて、設計図（`deck-spec.json`）に固める
- 作った後に、作った担当とは別のエージェント（AI の作業担当）が、スライドを画像にして見ながら点検する

作成そのものは、Anthropic が標準で提供する PowerPoint 作成 skill（`pptx` skill）で行う前提です。組織の標準テンプレートを使う作成 skill がある場合は、作成の段階だけを差し替えて、前後の流れはそのまま使えます。

## 2. 5 段階の流れ

| 段階 | 何をするか | 使う skill | 担当 |
|---|---|---|---|
| 1. 構成決定 | 聞き手・結論・各スライドの主張・図の型・強調する要素を決め、`deck-spec.json` に書く。検査スクリプトが終了コード 0 になるまで直す | `slide-composition-planner` | 作成側 |
| 2. 作成 | 設計図を渡して .pptx を作る。アウトライン（スライドごとの見出しの一覧）は設計図と突き合わせ、食い違えばどちらかを直す。ユーザーの承認はこの時点で 1 回だけ取る | 作成 skill（標準の `pptx` skill など） | 作成側 |
| 3. 分かりやすさの点検 | 主張と構成・文章量・視覚設計・根拠と図表・読みやすさを、画像を見ながら採点する | `slide-clarity-review` | 別のエージェント |
| 4. 日本語の点検 | スライドの文面の日本語（主語と述語、用語の説明、重複、文体、言い回し、折り返し）を点検する。日本語を含む資料のときに行う | `slide-japanese-review` | 別のエージェント |
| 5. 組織固有の検査（必要な場合） | 組織の配色・フォント・ロゴなどの規定を検査する。規定と検査手段がある組織だけが行う | 組織が用意する検査 | 別のエージェント |

- 段階 3 の `slide-clarity-review` は、利用者が `/slide-clarity-review` で起動します（Claude が自動では呼ばない設定です）
- 点検するエージェントには、作成時の会話を渡さず、ファイルの書き換えを禁止し、指摘だけを返させます。作る担当と点検する担当を分けるのは、自分で作ったものを自分で採点すると甘くなるためです
- 記事・報告書・メールなどの文章（散文）の日本語は、`stop-ai-slop-jp` で点検します。スライドには使いません（体言止めや箇条書きを減点する作りのため）

段階 1 の設計図は、`spec_version: 2` にすると、章立て（`sections`。同じ話題は 1 か所で説明する）、本文のスライドの目的と前提（`intent`）、改善の前後を示す例の型（`example`。前 → 起きたこと → 後 → 効果の順）、聴衆が使う素材の全文の置き場所（`exhibits`）、用語の一覧（`glossary`）、付録の順序（`role: appendix` と参考の区切り）も書けて、その整合が機械で検査されます。例や付録を含まない資料に、これらの項目を書く必要はありません。

## 3. 各 skill の役割と「1 skill 1 目的」の理由

| skill | 役割 | 担当しないこと |
|---|---|---|
| `slide-composition-planner` | 作る前の構成決定。設計図を出し、機械検査を通す | .pptx の作成、完成品の点検 |
| 作成 skill（標準の `pptx` skill など） | 設計図どおりに .pptx を作る | 点検 |
| `slide-clarity-review` | 完成品の分かりやすさの採点と、直し方の提案 | 日本語の文面、組織固有の規定 |
| `slide-japanese-review` | スライドの文面の日本語の点検 | 視覚設計、散文の日本語 |
| `stop-ai-slop-jp` | 散文の日本語の点検 | スライド |

skill を目的ごとに分けているのは、ソフトウェア開発でいう「単一責任の原則」（1 つの部品は 1 つの理由でだけ変更する）と、Unix の「1 つのことをうまくやる小さな道具を組み合わせる」という考え方に沿うためです。分けておくと、基準の見直しが他の点検に波及せず、作成 skill だけを組織のものに差し替える、といった組み替えもしやすくなります。

## 4. 点数の決め方

分かりやすさ（段階 3）と日本語（段階 4）は、どちらも 5 つの軸（観点）を各 20 点、合計 100 点で採点します。

**分かりやすさ（`slide-clarity-review`）**

- 根拠は、出典付きのベストプラクティス 33 項目（`.claude/skills/_shared/slide-best-practices.json`）です。そのうち 28 項目を完成品の点検で使い、残りの 5 項目は設計図の段階で検査します
- 一部の項目には適用条件があります（例: 「改善の前後を示す資料のみ」「外部の根拠を使う資料のみ」）。条件に当たらない資料では、その項目は対象外になり、減点も加点もしません。対象外にするには理由が要り、機械で条件が成り立つと分かる資料（例: 出典番号がある資料）では対象外にできません
- 機械検査は、点数に入る違反とは別に「候補」（空の枠、図形の重なり、所在の無い出典番号、複数の章に出る語、表のはみ出し）を出します。候補は点数に入れず、点検員が画像で確かめる手がかりにします
- 軸の点数は、「その軸が参照する項目の合否から計算した点」と「点検員が付けた点」の低い方です。計算は、20 点から、必須（must）の項目の不合格で 6 点、点検員が判定する推奨（should）の項目の不合格で 3 点、機械検査の推奨の項目の不合格で 2 点（違反したスライドが 3 枚以上なら 4 点）を引きます。点検員は根拠を引用して点を下げられますが、計算した点より上げることはできません
- 合格は「必須の項目の違反が 1 件もない」かつ「合計 80 点以上」です。95 点でも必須の違反があれば不合格です
- 合計が 70〜90 点（合格線の ±10 点以内）のときは、別の点検員にもう 1 回独立に採点させ、低い方を採ります。同じ版でも、点検員によって 10 点以上ずれることがあるためです

**日本語（`slide-japanese-review`）**

- ブロッカー（1 件で不合格になる重大な問題: 意味が取れない文、作業メモの露出、同じスライド内の意味の食い違い）が 0 件、かつ 80 点以上で合格です
- 75〜84 点のときは、別の点検員にもう 1 回採点させ、低い方を採ります

減点の大きさや合格線は暫定値で、実績を見て見直します。報告では、スクリプトが出した結果と、点検員が付けた点を分けて書きます。

## 5. 画像化の前提

スライドを画像にして見ないと、文字の不自然な折り返し、空白の多さ、同じ見た目の連続、強調と主張のずれを見落とします。そのため点検は画像を見て行います。

- 自動で画像にするには、LibreOffice（無償のオフィスソフト）と poppler（PDF を画像にする道具。`pdftoppm` を含む）が要ります。`slide-clarity-review/scripts/render_deck.py` が、PDF を経由してスライドごとの PNG 画像を作ります。場所は環境変数 `SOFFICE` / `PDFTOPPM`、または PATH から探します
- PowerPoint がある環境では、PowerPoint で PDF または画像として書き出したものを点検員に渡す方法もあります（このスクリプトは PowerPoint を自動では操作しません）
- どちらも使えない場合は、構造と文字だけで点検し、「描画未確認」と報告します。このとき、視覚設計と読みやすさの軸は 14 点を上限にします
- LibreOffice の描画は、フォントの置き換えなどで PowerPoint と折り返しが少し違うことがあります。折り返しの指摘には「描画ソフトの差の可能性」を添えます

## 6. 修正のルール

- 不合格なら、指摘を直し、新しい版名で保存して、もう一度点検します。**修正と再点検は最大 2 回**（点検は合計 3 回まで）です。それでも不合格なら止めて、残った指摘を報告します
- 直す担当も、スライドを画像にして見ながら直します
- 機械検査の数値を満たすことを目的にしません。次の抜け道は使いません: 順序や流れの図（矢印型の図・時系列）を表に置き換える、文字を表のセルへ移して文字量の検査を避ける、フォントを小さくして収める、重なりを消すために文字を画像にする、出典番号を消して候補を避ける、空の枠に意味の無い文字を入れる、条件に当たる資料で対象外を使う。直し方は、項目を減らす、文言を短くする、図を大きくする、スライドを分ける、所在を書く、枠を消す、のいずれかです
- **直すたびに点検し直します**。部分的な修正や、ユーザーの指摘による修正でも、確定前の点検（分かりやすさ・組織固有の検査・日本語）を別のエージェントで通し直します。上の「最大 2 回」は、3 種類の点検をまとめた 1 巡に当てます（どの点検の指摘で直しても 1 回と数え、直した後は 3 種類すべてを通し直します）
- 確定する前に、`finalize_review.py --verify-latest <確定する .pptx>` で、その版のハッシュと一致する PASS の記録があるかを確かめます。無ければ、その版は未点検として扱います。日本語と組織固有の検査は記録の仕組みが無いので、最終版に対して実行したことを報告に書きます

## 7. 他のプロジェクトへ入れる

### 依頼して入れる（推奨）

1. 入れたいプロジェクトの直下に、このリポジトリを `.setup-automate/` という名前で clone し、`.gitignore` に登録します（手順の詳細は [setup-guide.md](setup-guide.md)）
2. `.setup-automate/` の中で Claude Code を起動し、「親ディレクトリに資料作成キットを入れて」のように依頼します
3. 移植の手順（[setup-guide.md](setup-guide.md)）のうち、取り込む要素の選択で「資料作成キット」（由来台帳 `provenance.json` の `slide-creation-kit`）を選びます。次が対象に入ります
   - `.claude/skills/` の `slide-composition-planner`・`slide-clarity-review`・`slide-japanese-review` と、共有のデータ・スクリプト
   - この文書（`docs/slide-creation-kit.md`）
   - 下の「そのまま貼れるルール」を、対象の `CLAUDE.md`（Claude Code が毎回読む指示ファイル）に貼ったもの

### 手でコピーする

コピー先のプロジェクトのルートを基準に、同じ相対パスへ置きます。

| コピーするもの | 用途 |
|---|---|
| `.claude/skills/slide-composition-planner/` | 段階 1 |
| `.claude/skills/slide-clarity-review/` | 段階 3（画像化のスクリプトを含む） |
| `.claude/skills/slide-japanese-review/` | 段階 4 |
| `.claude/skills/_shared/slide-best-practices.json` と `.claude/skills/_shared/slide-sources/` | 点検の根拠（出典付き） |
| `.claude/skills/_shared/scripts/` の `slide_checks.py`・`validate_slide_data.py`・`append_review_record.py`（試験を回すなら `test_slide_skills.py` も） | 検査と記録 |
| `.claude/skills/_shared/review-record.schema.json`・`.claude/skills/_shared/review-rubrics.yaml` | 記録の形式と点数ランクの定義 |
| `docs/slide-creation-kit.md` | この文書 |
| `.claude/agents/readonly-reviewer.md`（任意） | 書き込みを禁止した点検用エージェント。無ければ `general-purpose` に「ファイルを作成・変更・削除しない」と明記して使う |
| `.claude/skills/stop-ai-slop-jp/`（任意） | 散文の日本語の点検。第三者のソフトウェアを同梱したもので、同じフォルダの `LICENSE`（MIT）と出自の表記を必ず一緒にコピーする |

コピーしたら、Claude Code を起動し直します（起動中に足した skill は読み込まれません）。スクリプトは、そのプロジェクトのルートから実行します。依存は Python と python-pptx（`pip install python-pptx`。完成品の文字の抽出は標準ライブラリだけで動きます）です。

## 8. そのまま貼れるルール

他のプロジェクトの `CLAUDE.md` に、次の節をそのまま貼れます。

```markdown
## 資料（スライド）を作るとき

流れ（手順の詳細は docs/slide-creation-kit.md）:
1. 作成前: `slide-composition-planner` で設計図（deck-spec.json）を作り、検査が終了コード 0 になるまで直す
2. 作成: 作成 skill（標準の `pptx` skill、または組織のテンプレート用の skill）で作る。ユーザーの承認はアウトライン提示時に 1 回
3. 作成後: `/slide-clarity-review` で、別のエージェントにスライドを画像にして点検させる
4. 日本語を含むときは `slide-japanese-review` で文面を別のエージェントに点検させる（散文は `stop-ai-slop-jp`）
5. 組織固有の配色・フォント等の規定があれば、その検査を別のエージェントで行う

守ること:
- 作る担当と点検する担当を分ける。点検役には作成時の会話を渡さず、書き換えを禁止し、指摘だけを返させる
- 合格は、必須の違反なし かつ 80 点以上。合格線の近く（分かりやすさは ±10 点、日本語は 75〜84 点）は別の点検員に再判定させ、低い方を採る
- 修正と再点検は最大 2 回（3 種類の点検をまとめて 1 巡と数える）。新しい版名で保存する。それでも不合格なら止めて報告する
- 直すたびに点検し直し、確定前に `finalize_review.py --verify-latest` で最終版の PASS の記録を確かめる
- 直すときも画像を見る。検査の数値を満たすために、図を表に置き換えない・文字を表に移さない・フォントを下げない
```

注: 「1 skill 1 目的」の理由として挙げた単一責任の原則と Unix の考え方は、一般的なソフトウェア設計の原則です。Anthropic の公式文書に同じ記述があることは確認できていません。点数の減点の大きさ・合格線・再判定の範囲は、2026 年 11 月時点の暫定値です。
