# /review-changes — 変更レビュー（エージェント分離実行）

> **このコマンドは別エージェントを起動してレビューを行う。現在のセッションでは直接レビューしない。**
> 実装コンテキスト（思考過程・設計判断・会話履歴）をレビューエージェントに渡さないことで客観性を確保する。

---

## 前提条件

- git リポジトリ内で実行する（git diff / git log が使える状態）。
- 評価基準は下記「既定の評価基準」（4 軸・配点・軸ごとの採点目安）を SKILL.md 内に持つので、本 skill 単体で動く。プロジェクトに評価基準ファイル（例: `workflows/software-development/review-changes.md`）があれば任意の補助として渡すが、軸・配点・判定表は既定のまま変えない。
- ツール: Bash（git 実行）・Read（設定ファイル読取）・Agent（レビュー起動）。コードの編集・実行はしない。
- `.claude/agents/readonly-reviewer.md` が無い環境では "general-purpose" で起動する（ステップ2）。

## 既定の評価基準

軸・配点・採点目安は常にこの表を使う。外部の評価基準ファイルがあっても、軸の増減や配点の変更には使わず、各軸の追加チェック項目としてのみ使う（同一入力で採点構造が揃うようにするため）。

| 軸 | 配点 | 見る点 |
|---|---|---|
| 1. 実装の正確性 | 30 | ロジックの正しさ、エッジケース、エラーハンドリング、セキュリティ |
| 2. テストカバレッジの網羅性 | 30 | テストの存在、正常系・異常系・境界値、副作用のモック分離、回帰テスト |
| 3. テスト品質・戦略 | 25 | 信頼性（フレーキーでないか）、アサーション品質、ハードコード検出、失敗シグナルの複数明示、テスト配置・実行経路の一意性 |
| 4. 変更の追跡可能性 | 15 | コミットメッセージ、ドキュメント整合、影響範囲 |

軸ごとの採点目安（配点に対する割合）: 90〜100% = 問題なし、または軽微な指摘のみ。70〜89% = 改善余地はあるが重大な欠陥なし。50〜69% = 重要な欠落や誤りが複数ある。50% 未満 = 軸の目的を満たしていない。証拠が足りない軸は該当レンジの下限で採点する。

## 実行手順

### ステップ1: 情報収集（この実装セッションで行う）

以下の事実情報のみを収集する。実装の意図・目的・設計判断の説明は**含めない**。

```
収集対象:
1. git diff HEAD~1 (直近コミットの差分)
2. git diff --cached (ステージ済み変更)
3. git diff (未ステージ変更)
4. git log --oneline -5 (直近5コミット)
5. 変更されたファイルの一覧と内容
6. テスト設定ファイルの検出と内容:
   - package.json / pyproject.toml / Cargo.toml / go.mod 等
   - jest.config.* / vitest.config.* / pytest.ini 等
   - .github/workflows/ 等のCI設定
7. （任意）プロジェクト固有の評価基準ファイル（例: workflows/software-development/review-changes.md）。無ければ省略し、既定の評価基準だけで進める
```

**スコープの優先順位:**
- ステージ済み変更がある場合 → ステージ済み + 直近コミットを主スコープとする
- ステージ済み変更がない場合 → 直近コミットの差分を主スコープとする
- 未ステージ変更は「参考」として記載するが主スコープには含めない

収集時の確認（次へ進む前のゲート）:
- git コマンドが失敗した場合（git 管理外・HEAD~1 が存在しない初回コミット等）は、エラー内容をユーザーに伝え、`git show HEAD` やファイルパス指定など取得できる範囲の差分に切り替える。
- 全ての diff が空の場合は、レビューエージェントを起動せず「レビュー対象の変更がない」とユーザーに報告して対象範囲（コミット範囲やファイルパス）を確認する。

引数が指定された場合:
- ファイルパスの場合 → そのファイルの変更に絞る
- コミット範囲（例: `HEAD~3..HEAD`）の場合 → その範囲の差分を使う

### ステップ2: レビューエージェント起動

**Agent ツール**を使い、以下の設定で別エージェントを起動する。起動に失敗した場合は、エラー内容を伝えたうえで subagent_type を "general-purpose" に変えて 1 回だけ再試行し、それでも失敗したら実装セッション内で代行せず中断して報告する:

```
Agent ツールの設定:
- subagent_type: "readonly-reviewer"（`.claude/agents/readonly-reviewer.md`。書き込み系ツールを持たない。定義が無い環境・新設直後で未読込のセッションでは "general-purpose" で起動し、prompt 冒頭に「ファイルを作成・変更・削除しない」と明記する）
- description: "Review changes objectively"
- prompt: 以下のテンプレートに収集した情報を埋め込む
```

**プロンプトテンプレート（レビューエージェントに渡す内容）:**

````
あなたは実装者とは別の客観的なシニアQAエンジニアです。
以下の変更に対し、実装の正確性とテストの網羅性を100点満点で評価してください。

## 行動原則
- Devil's Advocate: 「動いているから正しい」ではなく「本当に正しいか」を疑う
- 証拠主義: 推測でスコアを付けない。コードの事実のみで評価する。証拠不十分時は各レンジの下限で採点する
- 各軸のスコアには、該当するコード箇所（ファイルパスと行番号）を最低1つ以上引用し、減点理由・クリティカルイシューには diff またはコードの該当行を短く引用すること。引用できない指摘は出さない
- 非破壊: レビューのみ行い、コードの編集・実行は行わない
- 本スキルはコード実行を行わないため、テストのパス/フェイルは静的分析のみで判断する。CI結果が利用可能な場合はその情報も参照する

## 評価基準
[SKILL.md の「既定の評価基準」の表と採点目安を埋め込む。プロジェクト固有の評価基準ファイルがあれば、各軸の追加チェック項目として末尾に添える（軸・配点は変えない）。
 既定の4軸は次のとおり:
 - 軸1: 実装の正確性 (30点)
   - ロジックの論理的正確性 / エッジケース対応 / エラーハンドリング / セキュリティ
 - 軸2: テストカバレッジの網羅性 (30点)
   - テストの存在 / 正常系・異常系・境界値の網羅 / 副作用のモック分離 / 回帰テスト
 - 軸3: テスト品質・戦略 (25点)
   - 信頼性（フレーキーでないか） / アサーション品質 / ハードコード検出 / テスト戦略の適切さ
   - **失敗シグナルの複数明示**: 単一の broad な assertion だけでなく、戻り値・例外種別・エラーメッセージ内容・ログ出力・副作用の状態など複数の観点で bug 検出しているか
   - **テスト配置・実行経路の一意性**: 保存場所・実行方法が設定ファイル（jest.config / vitest.config / pytest.ini 等）で一意に定義されているか
 - 軸4: 変更の追跡可能性 (15点)
   - コミットメッセージ / ドキュメント整合 / 影響範囲]

## テスト基盤が未検出の場合
テスト基盤が検出できない場合、軸2・軸3は「テスト未導入のため0点。テスト導入を最優先提案とする」として採点すること。

## 採点・判定

| 評価 | 点数 | 判定 |
|------|------|------|
| S | 90〜100 | マージ可 |
| A | 80〜89  | 軽微な修正後にマージ可 |
| B | 70〜79  | 重点項目の修正が必要。再レビュー |
| C | 60〜69  | 大幅な修正が必要 |
| D | 59以下  | 設計からの見直しが必要 |
````

### ステップ3: 結果の報告

レビューエージェントから返却された結果を、そのままユーザーに表示する。
要約や解釈を加えない（レビューの客観性を維持するため）。

返却結果が上記「出力フォーマット」の見出し（総合評価・観点別採点・クリティカルイシュー・次のアクション）を欠いている場合は、欠けている節を指定して同じエージェントに再出力を 1 回依頼する。それでも揃わなければ、その旨を添えて受領した内容をそのまま表示する。

## Examples

- ユーザー: 「直近の変更をレビューして」→ `/review-changes` を引数なしで実行 → ステージ済み変更が無ければ直近コミットの diff + テスト設定を収集 → 別エージェントを起動 → 4軸スコアと次のアクションを表示。
- ユーザー: 「このファイルの変更だけ見て」→ `/review-changes path/to/file.ts` → その1ファイルの差分のみを収集対象とする。
- 差分が全て空の場合 → レビューエージェントを起動せず「レビュー対象の変更がない」と報告し、コミット範囲かファイルパスを確認する。
- 初回コミットで `HEAD~1` が無い場合 → `git show HEAD` に切り替えて差分を取り、その旨を基本情報に書く。
- テスト基盤が未検出のプロジェクト → 軸2・軸3を0点とし「テスト導入を最優先提案」と明記した結果を返す。

## 対象範囲（`review-implementation` との違い）

本スキルは**直近の変更差分**のみを評価する。プロジェクト全体の実装品質（マネタイズ・ペルソナ・UX 軸を含む）を評価したい場合は `/review-implementation` を使う。

## 注意事項

- **絶対に実装セッション内で直接レビューしない**。必ず Agent ツールで別エージェントを起動すること
- レビューエージェントに渡す情報は事実（コード差分・テスト設定）のみ。実装の意図・設計判断は渡さない
- 変更規模が小さい場合（10行以下）でも分離実行する。規模で判断しない
- エージェント構成の詳細は、リポジトリのルートに `agents.md` があれば任意で参照できる（無くてよい。起動手順はステップ2だけで完結する）
