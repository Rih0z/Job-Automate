# サーバー自動化 — WordPress管理システム構築・運用ワークフロー

認証情報 (SSH 鍵・DB パスワード) は利用する環境のものを使い、出力・ファイル・コミットに含めない。接続の初期設定が済んでいない場合は先に server-init を使う。

## 前提条件
- 対象は SSH が使えるレンタルサーバー上の WordPress。接続の初期設定は server-init で済ませてあること。
- wp-cli があれば使う。無い環境では `mysql` クライアントか wp-admin で代替する。
- プロンプトファイルの置き場 (`server/prompt/`) はこの skill の運用元 repo 固有の構成。無い環境では任意のディレクトリに同等の目的別プロンプトを用意して読み替える (skill には同梱しない)。
- バックアップ保存先はローカルの GitHub 管理下プライベートリポジトリ。

## プロジェクト概要

対象ブログはレンタルサーバー (SSH が使えるプラン) で運用されている WordPress サイト。Claude を使って
ローカル環境で記事の管理・編集・ファクトチェックを行うシステムを構築する。

## ユーザーの意図とプロジェクト目標

### 1. 基本的な管理システム構築
- **目的**: 対象ブログを Claude でローカル管理できるようにする
- **要件**: ローカル環境で編集 → 問題なければサーバーにアップロード
- **実現**: SSH接続によるファイル同期システム、バックアップシステム構築

### 2. 記事のバックアップとバージョン管理
- **目的**: 全記事をローカルにバックアップし、GitHub で管理
- **要件**: 元のHTMLフォーマットを維持してバックアップ（Markdown変換不要）
- **実現**: 完全なHTMLドキュメントとしてバックアップ、プライベートリポジトリに保存

### 3. 記事の品質向上とファクトチェック
- **目的**: HTML編集ガイドラインに基づいて全記事を更新
- **要件**:
  - 複数キャラクターによる解説追加（サイトの世界観に応じてキャラクター名・語尾を設定）
  - SEO最適化
  - ファクトチェック実施
  - 事実と感想の明確な分離
- **実現**: 自動処理システム構築、全記事に対してガイドライン適用

### 4. 本番環境への安全なアップロード
- **最重要要件**: 元のURLを変更せずに既存記事を更新
- **明確な制約**:
  - 新しいHTMLファイルの作成・公開は禁止
  - 存在しないURLの捏造は禁止
  - 元の記事を原則そのまま更新（インプレース更新）
  - 既存HTMLファイルの直接編集・更新のみ実施
- **期待する動作**: WordPress 上の既存投稿を更新する (主手段は wp-admin、DB 直接更新は上級者向けの代替。後述)

### 5. ファクトチェックの品質基準
- **要件**: 確認できた事実のみを記載
- **確認できた記事のみ**: 本番環境にアップロード
- **責任ある情報提供**: 事実と感想を明確に区別、信頼できる情報源の明記

## プロンプトシステム

目的別のプロンプトファイル (テーマ決定 / 業界情報収集 / HTML編集マスターガイド / アフィリエイト挿入 / 翻訳 / モバイル最適化 / ファクトチェック) を使い分ける。新規記事作成用は HTML ファイル作成可、既存記事更新用は作成禁止で、更新系は単独でなく統合して適用する。配置場所・一覧・分類・厳格ルールの詳細は [references/prompt-system.md](references/prompt-system.md) を読む。

## 記事更新ワークフロー

### 記事更新の重要な原則
- **自動更新スクリプトは使用しない** — 全ての更新はAIが個別に確認・処理
- **必ず更新前にバックアップを取る**
- **既存コンテンツは全て保持** — 情報量を減らさない
- **元の記事の価値を損なわない**
- **スクリプト作成前にユーザーに確認する** — 必要性を説明してから作成

### AIによる個別記事更新プロセス

**重要**: HTMLを更新する場合は、必ず用意されたプロンプトファイルを利用して、Claudeで更新する。

1. **更新対象記事の選定**
   - ユーザーが指定した記事、または文字化けが検出された記事から選択
   - 1記事ずつ丁寧に処理（一括処理は禁止）
2. **現在の記事内容を取得してバックアップ**
   - SSH でサーバーに入り、wp-cli が使えるなら `wp post get <post_id> --field=post_content > backup_<post_id>.html`
     で本文を保存する。wp-cli が無い場合は `mysql` で `SET NAMES utf8mb4;` を実行してから
     `SELECT post_title, post_content FROM <接頭辞>posts WHERE ID=<post_id>;` を実行し、結果を
     UTF-8 のファイルに保存する (テーブル接頭辞は wp-config.php で確認)。
   - 保存先はローカルのバックアップ用ディレクトリ (GitHub 管理下のプライベートリポジトリ)。
     ファイル名は `<post_id>_<日付>.html` とし、既存バックアップを上書きしない。
   - 成功判定: 保存ファイルの文字数が 0 でなく、日本語が文字化けせず読めること。満たさない場合は次へ進まない。
3. **AIによる内容理解と改善案作成**
   - 記事の全内容を読み込み、構造と内容を理解
   - 文字化け箇所を文脈から推測して修正
   - 上記の更新プロンプト群を適用し、各プロンプトの指示に従って包括的な改善を実施
   - 成功判定: 改善後の文字数がバックアップ以上であること (減っていれば削除箇所を洗い出して戻す)。
4. **ユーザーへの確認**
   - 主要な変更点を説明、必要に応じてプレビューを提示、ユーザーの承認を得てから実行
5. **安全な更新実行**
   - 手順 2 のバックアップが存在することを再確認してから更新する
   - WordPress管理画面からの更新が最も簡単:
     1. WordPress管理画面にログイン (wp-admin)
     2. 投稿一覧から該当記事を編集
     3. 改善されたコンテンツをコピー&ペースト
     4. 更新ボタンをクリック
   - キャッシュクリア、更新結果の確認 (公開 URL が変わっていないこと、文字化けが無いこと)

### ユーザーへの報告フォーマット
各記事の処理後、次のテンプレートで簡潔に返す。

```
対象記事: post_id / タイトル (変更なし) / URL (変更なし)
バックアップ: 保存先ファイル名 / 文字数
変更点の要約: 追加した要素 (ファクトチェック済みバッジ、確認済み事実セクション、キャラクター解説 等) / 修正した文字化け箇所
事実と感想の区別: 確認できた事実 / 感想・推測 / 使った情報源
文字数: 更新前 → 更新後 (減っていないこと)
結果: 成功 / 中止 (中止なら理由と次の対処)
```

### 使用例
- ユーザー: 「記事 ID 123 の文字化けを直してファクトチェックもして」
- 動作: 手順 2 で本文をバックアップ → 3 で化け箇所を修復し、ファクトチェックガイドと HTML 編集ガイドを適用 →
  4 で変更点と文字数 (例: 12,000 → 13,500) を提示 → 承認後に wp-admin で反映 → 公開 URL とキャッシュを確認して報告フォーマットで返す。

### 記事更新の技術要素
- ファクトチェック済みバッジ: 確認できた事実と個人的感想の明確な区別
- 複数キャラクターシステム: 役割ごとに語り口・語尾を分離（技術的情報担当／主観的感想担当／
  提案・楽しみ方担当 等）
- SEO最適化: 構造化データ、適切なメタデータ、内部リンク
- モバイルファースト: レスポンシブ対応、タッチフレンドリー、高速表示
- アフィリエイト統合: 読者価値を重視した自然な商品紹介

### 品質管理基準
- URL構造の完全保持（最重要）
- 既存コンテンツの価値向上
- 事実情報の正確性確保
- 読者体験の改善
- サイトパフォーマンス維持

## 過去の失敗から学んだこと（同じ失敗を繰り返さないための必読事項）

主な失敗は、(1) コンテンツ置き換えによる情報量の減少、(2) 文字エンコーディング事故、(3) キャラクター画像 URL の混在、(4) タイトルの勝手な変更。更新前に [references/failure-patterns.md](references/failure-patterns.md) を読み、対策と更新時の厳格なルールを確認する。必須の安全対策は、更新前バックアップ、WordPress リビジョンの活用、個別確認での段階的更新、更新後のキャッシュクリアと表示確認。

### 記事更新の実際の手順 (補足)

#### WordPress管理画面からの更新（推奨）
1. バックアップ — SSHでデータベースから現在のコンテンツをエクスポート
2. 管理画面アクセス — `https://<対象ドメイン>/wp-admin/`
3. 投稿編集 — 該当記事を検索して編集モードへ
4. コンテンツ置換 — 既存コンテンツを全選択して削除、新しいコンテンツを貼り付け
5. 更新 — 「更新」ボタンをクリック
6. キャッシュクリア — 必要に応じてサーバーキャッシュをクリア

#### データベース直接更新（上級者向け・代替手段）
- phpMyAdminやSSH経由でSQLを実行 (wp-cli なら `wp post update <post_id> <ファイル>`)
- UTF-8エンコーディングに注意 (`SET NAMES utf8mb4`)
- 必ずトランザクションで実行し、事前にバックアップを取る

### エラー時の対処とロールバック
- **文字化け・「?」表示**: 更新を中止。接続時の文字コード (`SET NAMES utf8mb4`) を確認してバックアップを取り直す。
- **SSH 接続失敗**: 鍵のパーミッション (秘密鍵は 600)、ホスト名・ポート、サーバー側の SSH 有効化を確認。解消しなければ `server-init` に戻る。
- **更新後に表示崩れ・情報欠落**: wp-admin の「リビジョン」から更新前の版に戻す。リビジョンが無ければバックアップ HTML を貼り直す。
- **キャッシュで古い表示が残る**: キャッシュプラグイン・サーバーキャッシュをクリアしてから再確認する。
