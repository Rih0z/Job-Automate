# 汎用ブログ記事レビュープロンプト（エージェント分離実行）

> **このスキルは別エージェントを起動してレビューを行う。現在のセッションでは直接レビューしない。**
> 実装コンテキスト（執筆意図・設計判断・会話履歴）をレビューエージェントに渡さないことで客観性を確保する。

対象: $ARGUMENTS

原本（評価軸・配点・ゲート条項・出力フォーマットの一次ソース）: `workflows/content-creation/review-blog.md`（リポジトリルートからの相対パス）

原本は数百行規模と長大なため、本 SKILL.md には要約も載せず、要点だけを `references/` に分けている（progressive disclosure）。
**採点の構造は原本の有無に関わらず `references/rubric.md`（評価軸・配点・0/4/9-gate・Must/Nice 減点・判定・N/A・第11項目のチェック ID）と `references/output-format.md`（出力の節構成）で決まる。** 原本がある環境では、これに加えて原本を Read させ、第1〜10項目の詳細チェックリストの補助に使う（食い違う細部は原本を優先）。原本が無い環境では references だけで同じ構造の採点ができる。
（参考: S/A/B/C/D 判定ラベルが最終的に何を意味するかの一般形は `.claude/skills/_shared/review-rubrics.yaml` の `verdict_scales.rank5_100` に集約している。本 skill の実際の点数帯・0/4/9-gate 即D判定は原本ファイルが唯一の SoT であり、上記共有ファイルはそれを上書きしない。）

## 前提条件

- 原本 `workflows/content-creation/review-blog.md` の有無は、ステップ1の前に Read（または Glob）で確認する。無い環境（skill だけ別リポジトリへコピーした場合など）では、`references/rubric.md` と `references/output-format.md` を基準として採点し、その旨を結果の補足コメントに「原本未参照」と書く。絵文字検出コマンド・業界規制トリガー表・第11項目のチェック ID も references に入っているため、0-gate・9-gate と Must/Nice 減点はどちらの環境でも同じ手順で再現できる。
- `.claude/agents/readonly-reviewer.md`（無ければステップ2のフォールバックを使う）。
- 原本・`.claude/skills/_shared/review-rubrics.yaml`・`readonly-reviewer` は repo 固有の任意資産。無くても `references/` の基準で採点でき、`readonly-reviewer` が無ければステップ2のフォールバックを使う。
- ツール: Read・Glob・Grep（記事と原本の読取）と Agent（レビュー起動）。書き込みはしない。

## 使用例

```
ユーザー: 「C:/work/drafts/qiita-sample.md を公開前レビューして」
→ ステップ1: 記事全文を Read し、設定欄を記入（プラットフォーム=Qiita、記事タイプ=技術解説 等）
→ ステップ2: readonly-reviewer を起動し、原本を Read させて採点
→ ステップ3: 総合評価（S〜D）・観点別採点・ゲート判定・修正箇所をそのまま表示
```

失敗系の例:
```
ユーザー: 「drafts/missing.md をレビューして」
→ ステップ1: Read が失敗 → 絶対パスの再確認を依頼し、読めるまでレビューへ進まない
ユーザー: 「(原本の無い別リポジトリで) この記事を採点して」
→ references/ の基準で採点し、補足コメントに「原本未参照」と明記する
```

エッジケース: 記事が未完成（見出しだけ等）の場合は、N/A 処理ルールの対象かを原本で確認させ、採点不能な項目は N/A として扱わせる。9-gate に該当する記述（機密情報・規制NG表現）が見つかった場合は、他の点数に関わらず即D判定のまま報告する。

## 実行手順

### ステップ1: 設定欄の記入 + 情報収集（この実装セッションで行う）

原本冒頭の「設定欄」（プラットフォーム軸 × 業界軸 × 記事タイプ軸 × 運用軸の4ブロック）を、対象記事から読み取れる範囲で記入する。不明な項目は執筆者に確認するか「不明」と明記する。対象記事のパスが無効・読めない場合は、絶対パスをユーザーに再確認し、読めるまでレビューへ進まない。

以下の事実情報のみを収集する。執筆意図・設計判断の説明は**含めない**。

```
収集対象:
1. レビュー対象記事ファイルの内容全文（MD / HTML 等）
2. 設定欄の記入値（A.プラットフォーム軸 / B.業界軸 / C.記事タイプ軸 / D.運用軸）
3. 記事タイプ（原本「記事タイプ別 N/A 早見表」のどれに該当するか）
```

### ステップ2: レビューエージェント起動

**Agent ツール**を使い、以下の設定で別エージェントを起動する:

```
Agent ツールの設定:
- subagent_type: "readonly-reviewer"（`.claude/agents/readonly-reviewer.md`。書き込み系ツールを持たない。定義が無い環境・新設直後で未読込のセッションでは "general-purpose" で起動し、prompt 冒頭に「ファイルを作成・変更・削除しない」と明記する。Agent 起動自体が失敗したら、エラーを伝えて 1 回だけ再試行し、だめなら実装セッション内で代行せず中断して報告する）
- description: "Review blog article objectively"
- prompt: 以下のテンプレートに収集した情報を埋め込む
```

**プロンプトテンプレート（レビューエージェントに渡す内容）:**

```
あなたは執筆者とは別の客観的なブログ記事レビュアーです。
以下の記事を、評価基準ファイルに定義された11観点・110点満点 + 3ゲート条項（0-gate/4-gate/9-gate）で
採点してください。レビュワーは元ファイルを絶対に編集してはならない。フィードバックの提供のみ行う。

## 評価基準ファイル（必ず Read してから採点すること。要約・省略・改変禁止）
1. `.claude/skills/review-blog/references/rubric.md` と `references/output-format.md`（常に Read する。採点構造の正本）
2. workflows/content-creation/review-blog.md（このリポジトリのルートからの相対パス。呼び出し元セッションの作業ディレクトリを基準に解決すること。存在する場合だけ追加で Read し、第1〜10項目の詳細チェックリストの補助にする。食い違う細部は原本を優先）
原本が存在しない場合は、出力の補足コメントに「原本未参照」と書くこと。

上記ファイルを Read し、以下を一言一句そのまま適用すること:
- レビュー前の設定欄（A.プラットフォーム軸 / B.業界軸 / C.記事タイプ軸 / D.運用軸）
- 0-gate プラットフォーム固有制約チェック（絵文字検出コマンド含む）
- 冗長性チェック
- 11項目・計110点満点の評価観点（各項目の配点・チェックリスト）
- 4-gate（外部主体の財務・採算性・戦略判断の断定）
- 9-gate（コンプライアンス・機密情報、業界規制NG表現トリガー表）
- 第11項目のサブセクション別配点（モード別 SoT: 通常/整合性検証/軽量化）
- N/A処理ルール（項目全体/サブセクション/サブ項目の3段階、100点換算式）
- 記事タイプ別 N/A 早見表
- 採点方法（S/A/B/C/D判定、ゲート条項による即D判定）
- レビュー結果出力フォーマット（基本情報・総合評価・観点別採点・第11項目サブセクション別採点・
  技術評価の妥当性 詳細チェック・良かった点・改善提案・具体的な修正箇所・補足コメント）
- Phase 4b（外部主体断定がある場合の公式反論・否認検索、4-gate対応）を必要に応じて実施

## 対象記事
[ここにレビュー対象記事の内容全文を埋め込む]

## 設定欄記入値（ステップ1で収集）
[ここに A/B/C/D 軸の記入値を埋め込む]

## 出力
評価基準ファイルの「レビュー結果出力フォーマット」に完全準拠した構造化レビューレポートを出力すること。
減点・ゲート判定・指摘ごとに、根拠となる記事内の該当箇所（見出し名または行番号と、短い引用）を必ず添えること。引用できない指摘は行わない。
```

### ステップ3: 結果の報告

レビューエージェントから返却された結果を、そのままユーザーに表示する。要約や解釈を加えない（レビューの客観性を維持するため）。

返却結果に含まれているべき節（出力フォーマットの本体は原本が SoT。ここは受領時の確認用チェックリスト）:

| 節 | 確認すること |
|---|---|
| 基本情報 | 設定欄の記入値が反映されている |
| 総合評価 | S〜D の判定と、ゲート（0-gate / 4-gate / 9-gate）の該当有無 |
| 観点別採点 | 11観点すべての得点または N/A |
| 第11項目サブセクション別採点・技術評価の妥当性 詳細チェック | 該当時のみ |
| 良かった点・改善提案・具体的な修正箇所・補足コメント | 指摘ごとに記事内の該当箇所の引用がある |

返却結果に原本の出力フォーマットの主要節（総合評価・観点別採点・改善提案）が欠けている場合は、欠けた節を指定して同じエージェントに 1 回だけ再出力を依頼する。

## 注意事項

- **絶対に実装セッション内で直接レビューしない**。必ず Agent ツールで別エージェントを起動すること
- `references/` は原本の要点を採点に必要な範囲で写したもの。原本更新時は食い違わないよう同期する（細部が食い違うときは原本を優先）
- レビューエージェントに渡す情報は事実（記事本文・設定欄記入値）のみ。執筆意図・設計判断は渡さない
- 評価軸・配点・ゲート条項・出力フォーマットは上記の評価基準ファイルの記述どおりに適用し、要約・改変しない
- レビュワーは元ファイルを絶対に編集してはならない（フィードバックの提供のみ）
- 冗長・スコープ不明確と判断した場合は、レビュー実施前に執筆者へ意図確認する（原本「冗長性チェック」参照）
