# マルチテナント・テンプレート注入

## 課題

提案書・記事・資料等を複数のクライアント/組織向けに同じ構成で作る際、うっかり**あるクライアント向けの確定文面(社名・免責事項・連絡先・関連リンク等)を、別クライアント向けの成果物に流用してしまう**事故(テナント間 leak)が起きやすい。特にテンプレートを直接コピーして手直しする運用では、修正漏れが発生しやすい。

## 設計原則: 2層分離

1. **共通形式層(テンプレート本体)**: どのクライアントにも共通する構成・見た目・章立て・機械的な変換ロジック。**特定クライアントの固有文言をここに一切書かない**。
2. **クライアント固有層(設定ファイル)**: `clients/<client-id>/required-sections.md` のような、クライアントごとに分離した設定ファイルに、確定文面(免責事項・署名欄・連絡先・関連リンク等)と用語マッピング(社内呼称の言い換え等)を持たせる。

注入skill(本パターンを実装する側)は「どのクライアントの・どの確定文面を・どの位置へ」を**解決するだけ**の役割に徹し、確定文面そのものを保持しない。

## 設定ファイルの書式

`clients/<client-id>/required-sections.md` は、1 セクション 1 見出しで書く。この書式はこのリポジトリが固定するものではなく、設計時の例である。既存の設定ファイルがある場合は、その書式を優先する。

```markdown
# <client-id> 必須セクション

## 免責事項
(逐語で注入する確定文面)

## フッター
(逐語で注入する確定文面)

## 用語マッピング
| 標準の呼称 | このクライアントでの呼称 |
|---|---|
```

テンプレート側には、`{{section:免責事項}}` のように見出し名を指すプレースホルダだけを置く(記法はプロジェクトの既存のものに合わせてよい)。

## 実装手順

1. **アクティブなクライアントの確定**: クライアント ID は、ユーザーの明示的な指定、または成果物に書かれた宛先から確定する。未指定のまま生成しない。default で黙って特定クライアントの文言を使わない。複数のクライアント ID が候補になるときは、ユーザーに確認する。
2. **クライアント設定ファイルを Read する**: `clients/<client-id>/required-sections.md`(または同等の設定ファイル)から、必須セクションの確定文面・用語マッピングを取得する。
3. **leak防止(最重要)**: アクティブなクライアント**以外**の設定ファイルの内容を絶対に使わない。解決経路が曖昧な場合は生成を止めてユーザーに確認する。
4. **確定文面はそのまま逐語で注入**する(独自の言い換え・要約をしない)。記事固有の一文追記のみ許容する。
5. **注入後の検証**: 注入したセクションが設定ファイルの確定文面と逐語一致しているか確認する。また、他クライアントの社名・連絡先・URL等が誤って混入していないかを別エージェントで検査する(自己レビュー不可)。検証結果には、確認したファイルと該当箇所(`ファイル名:行番号` または見出し名)を添える。

## エラー時の対処

- `clients/<client-id>/required-sections.md` が無い: 生成を止める。「設定ファイルが無い」ことと探したパスを報告し、他クライアントの設定で代用しない。新規作成は、確定文面をユーザーから受け取ってから行う。
- 必須セクションが設定ファイルに無い: そのセクションを空欄のまま出力せず、不足している見出し名を報告して止める。文面を創作して補わない。
- 注入結果が設定ファイルと逐語一致しない: 注入し直す。それでも一致しない場合は、差分(設定ファイルの該当行と成果物の該当行)を示して報告する。
- 別クライアントの固有名詞・URL・連絡先が混入していた: 成果物を確定させず、混入箇所を示して取り除く。取り除いた後、手順 5 の検証をやり直す。

## 使用例

- 依頼: 「A 社向けと B 社向けで同じ提案書テンプレートを使いたい」。手順 1 でクライアント ID を確認し、`clients/<client-id>/` を作る構成を提案する。テンプレート本体にはプレースホルダだけを置き、各社の文面は設定ファイル側に置く。
- 依頼: 「この提案書に免責事項を入れて」でクライアントが決まっていない場合。生成せず、どのクライアント向けかを聞き返す。

## 注入結果の報告形式

生成後、次の項目を報告する。

| 項目 | 内容 |
|---|---|
| クライアント ID | 確定した ID と、その根拠(ユーザー指定 / 成果物の宛先) |
| 参照した設定ファイル | パス |
| 注入したセクション | 見出し名と挿入位置 |
| 逐語一致の確認 | 一致 / 不一致(不一致なら差分) |
| 他クライアントの混入検査 | 検査者(別エージェント)の結果 |

## 新規クライアントの追加

新しいクライアントを追加する場合、注入skill本体は変更不要。`clients/<new-client-id>/required-sections.md` を新設し、確定文面を記載するだけで、以後は自動的にそのクライアント向けの文言が解決・注入される(=スケールしても既存コードを触らない設計)。

## チェックリスト

- [ ] テンプレート本体(共通層)に特定クライアントの固有名詞・URL・連絡先がハードコードされていないか
- [ ] アクティブなクライアントの解決結果が曖昧なまま生成を進めていないか
- [ ] 注入後、他クライアントの文言が混入していないか(別エージェントで検査)
- [ ] 確定文面が設定ファイルと逐語一致しているか(独自改変がないか)
