# スライドの日本語点検（スライド専用）

対象: $ARGUMENTS（.pptx の絶対パス）

> **採点は別エージェント（`readonly-reviewer`）に任せる。** 現在のセッションで採点しない。作成の意図・会話履歴は渡さない。点検するエージェントは、ファイルを作成・変更・削除せず、指摘だけを返す。修正は作成側セッションが、そのスライドを作った生成 skill で行う。

## この skill を作った理由と、他の skill との境界

散文用の日本語点検（`stop-ai-slop-jp`）は、文のリズムの揃い、体言止めの連続、箇条書き、短文の連続を減点する作りで、スライドでは普通の書き方まで不利になる。そこで、スライドの文面だけを対象にした別の基準を持つ（1 つの skill には 1 つの目的を持たせる）。

- 散文（記事・報告書・メール）の日本語: `stop-ai-slop-jp`
- 分かりやすさ（主張、文章量、視覚設計、図表、可読性）: `slide-clarity-review`（この skill の前に通す）
- 組織固有の配色・フォント・ロゴの規定: 組織が用意する検査（ある場合のみ。この skill では扱わない）
- スライドの文面の日本語: この skill

資料作成の流れ全体（構成決定 → 作成 → 分かりやすさ → 日本語 → 組織固有の検査）は `docs/slide-creation-kit.md`。その文書が無い環境では読み飛ばす。

## 前提条件

| 前提 | 用途 | 無いとき |
|---|---|---|
| Python 3（標準ライブラリのみ） | 抽出と機械検査 | 実行できなかったと報告して停止する |
| 同じリポジトリの `slide-clarity-review`（`scripts/extract_deck.py`・`scripts/render_deck.py`） | 文面の抽出・画像化 | 同じ形の JSON（スライドごとの `no`・`title` と、位置順の `text_blocks`）を別に用意する |
| LibreOffice と poppler（`pdftoppm`）、または PowerPoint | 画像化（折り返しの確認） | 「描画未確認」と報告する |
| 読み取り専用の点検用エージェント `readonly-reviewer`（`.claude/agents/`） | 採点 | `general-purpose` に「ファイルを作成・変更・削除しない」と明記して使う |

コマンドは、この skill を置いたリポジトリのルートからの相対パスで書いている。別のプロジェクトでは、`slide-clarity-review` と一緒に同じ相対パスへ置く。

## してはいけないこと

- 現在のセッション（作成した側）で採点する。点検員に作成の意図や会話履歴を渡す
- 点検員にファイルを作成・変更・削除させる
- 引用の無い点数、軸の欠けた返却を採用する（出し直しを依頼する）
- 体言止め・箇条書き・短文の連続を、それだけで減点する
- 点検員の結果を要約し直して緩める。75〜84 点で再採点を省く
- 修正と再点検を 2 回を超えて続ける

## 手順（リポジトリのルートから実行）

1. **文面の抽出**: `python .claude/skills/slide-clarity-review/scripts/extract_deck.py <deck.pptx> -o <作業dir>/deck-facts.json`。`text_blocks` に、画面の位置順（上から下、左から右）の文面が入る（図形ごとの段落と、表のセルを含む）。
2. **機械検査**: `python .claude/skills/slide-japanese-review/scripts/check_ja_slide.py <作業dir>/deck-facts.json -o <作業dir>/ja-auto.json`（終了コードは常に 0。指摘の件数と一覧を標準出力に出す）。検出するもの: 敬体と常体の混在、重複（同じスライド内の完全一致を含む）、全角・半角の括弧の混在、番号だけの参照（表のセルを含む）、全角ダッシュ、作業メモ・プレースホルダーの候補（`criteria/memo-words.json`）、常套句。言い換えの重複は検出できない。「検出なし」は「問題なし」ではない。
3. **画像化（できる場合）**: `python .claude/skills/slide-clarity-review/scripts/render_deck.py <deck.pptx> -o <作業dir>/images`（LibreOffice で PDF にし、poppler の `pdftoppm` で画像にする。PowerPoint で書き出した画像でもよい）。折り返しの確認に使う。描画ソフトによる差があるため、折り返しの指摘は「描画での指摘」と明記する。描画できなければ（終了コード 2）「描画未確認」と報告する。
4. **別エージェントで採点**: `readonly-reviewer` を起動し、次の入力だけを渡す。`deck-facts.json` の各スライドの `title` と `text_blocks`、`ja-auto.json`、`criteria/axes.json`（軸・点数の目安・ブロッカーの判定方法）、画像があればそのパス。返却形式: `{"axes":[{"id","score","citations":["slide 3: 原文"]}],"blockers":[{"id","slide","quote","reason"}],"fixes":[{"slide","problem","fix"}]}`。各軸 0〜20 点。**満点の軸にも、確認した箇所の引用を 1 件以上付ける**（引用の無い点数は無効。出し直しを依頼する）。タイトルが空のスライド（終了スライドなど）は、採点の対象から外し、その旨を報告する。
5. **ゲート**: ブロッカー 0 件、かつ 80 点以上で合格。ブロッカーが 1 件でもあれば、点数に関係なく不合格とし、点数と別に報告する。75〜84 点の場合は、割れやすいため、別のエージェントにもう 1 回独立に採点させ、低い方を採る。数え方の規則（同じ原因の数え方、折り返しの数え方、採点の対象外のスライド）は `criteria/axes.json` の `counting_rules`。80 点と点数の配分は暫定値で、実績で見直す。
6. **修正**: 不合格なら `fixes` を作成側が適用し、新しい版名で保存して手順 1 からやり直す。**修正と再点検は最大 2 回**。それでも不合格なら止めて、残りを報告する。資料作成の流れの中では、分かりやすさ・組織固有の検査・日本語の 3 種類の点検をまとめて 1 巡と数える（流れの文書 `docs/slide-creation-kit.md` が正）。

## 減点しないもの（スライドでは普通の書き方）

体言止め、箇条書き、短い文の連続、リズムが揃っていること、見出しの対句、矢印（→）、リード文は敬体で見出しと箇条書きは体言止めという組み合わせ。減点するのは、体言止めのせいで「何がどうなるか」が読み取れない場合だけである（軸 1）。

## 軸とブロッカー

軸（各 20 点。正本は `criteria/axes.json`）: 1 主語と述語の対応、2 用語・略語・参照先の説明、3 簡潔さと重複、4 文体と表記の一貫性、5 言い回しの自然さ。点数の目安（指摘 0 件で 20、1〜2 件で 15〜19 など）も同ファイルにある。

- 軸 2 は、聴衆の前提知識から見て専門的な語（分野の専門用語・組織内の呼び名・略語）が、初出のページで説明されているか（または用語の一覧へ案内しているか）も見る。用語の初出の説明は、この軸が正（`slide-clarity-review` には同じ観点を置かない）
- 軸 3 は、同じ文・同じ内容の言い直しを数える。同じ話題が離れた章に分かれて出る構成の問題は `slide-clarity-review` の `one-topic-one-place` が見る（二重に減点しない）

文字の折り返しの不自然さ（1〜2 文字だけが次の行に落ちる、語の途中で改行される）は、描画できたときに軸 5 の指摘として数える。

ブロッカー（1 件で不合格）: B1 意味が取れない文、B2 作業メモ・内部語彙の露出、B3 同じスライド内の意味の食い違い。判定の仕方は `criteria/axes.json` の `how_to_decide`。見出しと本文が食い違う場合は、意味が 2 通りに読める（B3）か、単なる不一致（軸 1 の減点）かを、`how_to_decide` に従って分ける。

## 出力

ユーザーへの報告は次の形で書く。機械検査の結果（`ja-auto.json`）と、点検員の採点は分けて書く。

```markdown
## スライドの日本語点検: <ファイル名>
- 合否: 合格 / 不合格（ブロッカー N 件、合計 NN 点。再採点した場合は 1 回目 NN 点・2 回目 NN 点で低い方を採用）
- 描画: 確認済み / 描画未確認

### 軸ごとの点数（点検員）
| 軸 | 点数 | 確認した箇所の引用 |
|---|---|---|
| 主語と述語の対応 | NN/20 | slide N: 「…」 |
（5 軸すべて）

### ブロッカー
| id | スライド | 原文 | 理由 |

### 指摘と直し案
| スライド | 問題 | 直し案 |

### 機械検査（参考。採点ではない）
- <check>: slide N 「…」

### 採点の対象外にしたスライド
- slide N（理由）
```

## エラー時

| 状況 | 対処 |
|---|---|
| .pptx が開けない・存在しない | 実行せず、正しい絶対パスを求める |
| `extract_deck.py` が無い（`slide-clarity-review` を入れていない） | 同じ形の JSON を用意するか、`slide-clarity-review` を入れるよう案内して停止する |
| `readonly-reviewer` を起動できない | `general-purpose` で再試行し、prompt に「ファイルを作成・変更・削除しない」と明記する。それでも失敗したら未実施と報告し、現セッションで代替採点しない |
| 点検員の返却に引用の無い軸がある・軸が欠ける | その点数を使わず、欠けている項目を示して出し直しを依頼する |
| 画像化できない | 文面だけで点検し、「描画未確認」と書く（折り返しは採点しない） |

## 使用例

「`C:\decks\plan.pptx` の日本語を点検して」 → 文面を抽出 → 機械検査（敬体と常体の混在 1 件、番号だけの参照 1 件）→ 画像化 → `readonly-reviewer` が 5 軸を採点（82 点・ブロッカー 0 件。75〜84 点なので別の点検員が再採点し 78 点）→ 低い方の 78 点で不合格 → `fixes` を生成 skill で適用し新しい版名で保存 → 再点検で 86 点・合格 → 報告。

「画像にできない環境で点検して」 → `render_deck.py` が終了コード 2 → PowerPoint で書き出した画像も無い → 文面だけで点検し、報告の「描画」を「描画未確認」にする（折り返しは採点しない）。

点検員が 1 つの軸に引用を付けずに 20 点を返した → その返却を採用せず、引用の欠けた軸を示して出し直しを依頼する。
