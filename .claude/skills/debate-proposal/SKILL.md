# /debate-proposal — 新規提案の多視点議論 + 裁定 (エージェント分離実行)

対象: $ARGUMENTS

> **このスキルは別エージェントを 3 本起動して議論させ、現在のセッションは統合と裁定だけを行う。**
> 提案の発案経緯・会話履歴・期待する結論は論者に渡さない (Writer/Reviewer 分離の原則を「提案の採否判断」に適用したもの)。

## 目的

「思いついた案を即実装して再テストすべきか」を、実装者 (= 本セッション) の思い込みや会話の勢いで決めず、
**互いに独立した 3 つの視点** (採用を最強に論証する側 / 不採用を最強に論証する側 / 前例調査と中立裁定) に
同じ一次資料だけを渡して議論させ、一致点 (converged) と対立点 (contested) を分けて裁定する。
議論の素材は必ず repo 内の一次資料 (実装コード・実測ログ・Issue・設計書・参照 OSS) と literal 引用に限定し、
「気がする」「はず」で採否を決めない。

## 適用範囲

- 適用する: 新機構の追加提案、既存機構の置換案、方針転換 (「A をやめて B にする」)、実行中のテスト・作業の
  中断・切替判断を伴う案
- 適用しない: typo / 軽微修正 / 既に設計書 + 独立レビューが PASS 済みの案 (その場合は `review-gate` の設計工程) /
  成果物そのもののレビュー (`review-*` skill の領域)

## 原則

1. **中立記述が先**: 提案は賛否の結論を含まない中立文に書き直してから議論に出す (Step 1)。依頼者の原文を
   そのまま渡すと「依頼者が望んでいる結論」が漏れて論者が迎合する。
2. **同じ一次資料、違う役割**: 3 論者には同一の path 一覧を渡す。役割 (推進 / 反対 / 裁定) だけを変える。
   推進側にも「不利な事実は隠さず弱点として明記」、反対側にも「有利な事実は利点として明記」を課す (ごまかし防止)。
3. **proof-by-presence**: 全主張に `<file>:<line>` literal 引用 + 確信度 (VERIFIED / SUSPECTED / REFUTED)。
   「見つからなかった」は proof by absence なので、調査した path を明記させ「存在しない」とは書かせない。
4. **既存実装との重複切り分けを必須化**: 提案の各要素が「実装済 / 未実装 / 意図的に不採用 (理由付き)」の
   どれかを行番号付きで判定させる (観点⑤の具体化。過去に試して却下された設計の再提案を検出する)。
5. **前提の事実検証**: 提案が依拠する因果 (例:「長くなると遅くなる」) は一次データで検証させる。
   前提が REFUTED なら処方の議論より先にそれを報告する。
6. **数値の出所照合**: 複数の論者が同じファイルから別の数値を引いたら、統合前に本セッションが一次資料で
   どちらが正しいか (または両方正しく対象が違うのか) を確定する。
7. **実機負荷への配慮**: 重い処理 (実機テスト・ビルド等) の実行中は論者に「再帰 grep 禁止 / スクリプト実行禁止 /
   Read・Glob 優先」を literal で課す。

## 手順

### Step 0: 前提確認 (本セッション)

提案が「実行中のテスト・作業を止めるか」を含む場合、先にその**現在状態**をログ (完了マーカー / 実行ログ) で
確認する。既に終了・失敗している場合は Q2 を「対象消滅」に差し替え、終了理由を Step 1 の一次資料に加える。
並走セッションの痕跡確認 (同一対象への他セッションの作業有無) は、本 repo に規定があればそれに従う。

### Step 1: 中立提案ファイルの作成 (本セッション)

作業用ディレクトリ (例: `.tmp/review/`) に `proposal_<topic>_<YYYYMMDD>.md` を Write する。**賛否の結論・本セッションの
見立ては書かない**。構成:

```markdown
# 検討対象: 提案「<短い名前>」
## 提案内容 (原文の趣旨)          ← 中立に書き直す。何を・どの層で・何のために
## 検討すべき問い
- Q1. この案を今すぐ実装して再テストすべきか (すべきでないなら、いつ・どの条件で)
- Q2. <実行中のテスト/作業を止めて切り替えるべきか — 該当する場合のみ>
- Q3. 既存 OSS (参照 clone / 参照メモ) に同種の実装があるか。層 (会話履歴 / セッション / 永続化 等) を分けて
## 事実確認に使う一次資料 (path のみ。内容は各自 Read)
- 現行実装: <該当モジュールの絶対 path>
- 関連 Issue / 設計書 / 実測ログ / 過去の判断記録
- OSS 参照: <参照 OSS の index or clone の特定ファイル>
- 評価基準: 5 観点 (①対症療法でないか ②超長期的に最適か ③業界標準と整合するか ④セキュリティ懸念 ⑤既存実装を活かせないか)
```

### Step 2: 3 論者の並列起動 (Agent tool、1 メッセージで 3 本同時)

全員 `subagent_type: general-purpose` (設計判断を伴う分析のため、利用可能なら最上位モデルを指定)。
**会話履歴・本セッションの見立て・依頼者の原文は渡さない**。共通部 + 役割部で構成する。

**共通部 (3 本に同一)**:

```
提案ファイル (絶対パス、必ず最初に全文 Read): <Step 1 の path>
repo root: <絶対 path>
出力: 各主張に <file>:<line> literal 引用 + 確信度 (VERIFIED / SUSPECTED / REFUTED)。
「なし」と判定する場合は調査した path を明記 (proof by absence を verdict にしない)。
運用制約 (literal): 読み取り専用 (コード変更・ファイル作成・プロセス操作・git 書込 禁止)。
<重い処理の実行中なら: repo 全体への再帰 grep 禁止、Grep は path+glob 限定、スクリプト/ビルド/テスト実行 禁止>。
会話履歴は与えられていない。期待される結論も与えられていない。Read した一次資料のみを根拠にすること。
```

**役割部**:

| 論者 | 課すこと | 出力節 |
|---|---|---|
| 推進側 | 採用すべき最強の論証。不利な事実は「反対側が指摘しうる弱点」として明記した上で反論。効果を**数値**で予測 (一次データから) | 1 提案の分解 (実装済/未実装、行番号) 2 採用論拠 3 弱点と反論 4 Q1/Q2/Q3 verdict 5 最小実装案 + 再テスト設計 (何を測れば効果判定できるか) |
| 反対側 | 今すぐ採用すべきでない最強の論証。**提案の前提となる因果を一次データで検証** (原因帰属を数値で)。有利な事実は「推進側が主張しうる利点」として明記した上で反論 | 1 前提の事実検証 2 不採用論拠 3 利点と反論 4 Q1/Q2/Q3 verdict 5 代替案 (提案より先にやるべきこと、コスト昇順) |
| OSS 調査 + 中立裁定 | 賛否どちらの立場も与えない。OSS ごとに提案の各要素 (例: ①保存 ②クリア ③再開) の実装有無を表にし、本 repo 既存実装との差分を行番号で示す。5 観点で独立採点 | 1 OSS × 要素 表 2 既存実装との差分 3 5 観点評価 4 Q1/Q2/Q3 verdict 5 推奨 (採用 / 不採用 / 条件付き + 条件) |

### Step 3: 統合 (本セッション) — 3 本の結果が揃ってから

1. **数値照合** (原則 6): 論者間で同一ファイルからの引用値が食い違えば、本セッションが一次資料を Read/grep して
   確定する (例: 同じタグで証跡が上書きされ別の実行結果を見ていた、等)。食い違いの原因自体が発見なら
   本 repo の発見メモ queue に記録する。
2. **converged / contested の分離**: 3 者が一致した事実・判断を先に列挙し、次に対立点を「誰が・何を根拠に」の形で
   並べる。一致点は verdict の土台、対立点は条件・順序の問題として扱う。
3. **裁定**: Q ごとに 1〜3 文。「採用 / 不採用 / 条件付き採用 (条件を列挙)」+ 着手条件 + 提案より先にやるべき
   安価な打ち手 (反対側 5 節) を採る。**採用に傾く場合も「提案そのまま」ではなく、既存実装の拡張として
   最小の差分に絞り直す** (二重経路を作らない + 観点⑤)。
4. **第 2 ラウンド (任意)**: 対立点が事実認識の差なら `SendMessage` で各論者に他 2 者の該当節 (匿名化) を渡して
   再反論させる。判断の差 (価値観・優先順位) なら第 2 ラウンドは回さず依頼者の判断に上げる。

### Step 4: 出力 (本セッション → 依頼者)

```markdown
## 議論の統合結果 (3 論者)
**全員一致**: - ... (各 1 行、根拠 path 付き)
**対立点**: - 推進側: ... / 反対側: ... / 中立: ...
**裁定**: Q1 = <採用/不採用/条件付き> (理由 1〜3 文 + 着手条件) / Q2 = ... / Q3 = ...
**先にやるべき打ち手** (コスト昇順): 1. ... 2. ...
**発見事項** (queue 済): - ...
```

### Step 5: 後続の routing (本セッション)

| 裁定 | 次の action |
|---|---|
| 採用 / 条件付き採用 | 設計書を起こし `review-gate` の設計工程へ。裁定の「条件」を設計書の前提条件節に転記 |
| 不採用 | 該当 Issue (あれば) の「検討済み代替案」節に裁定要旨 + 議論ログの path を追記。再検討条件も書く (同じ案が再提案された時に議論を繰り返さないため) |
| 対象消滅 (Q2) | 消滅理由 (失敗・中断) の原因を Issue 化し、元のテスト/作業の取り直しを優先 |

いずれも議論の 3 レポートは `<作業用ディレクトリ>/debate_<topic>_<YYYYMMDD>/` に `proponent.md` / `skeptic.md` / `arbiter.md`
として保存し、Issue / 設計書からはその path を参照する (本文へ全文転記しない)。

## 完了条件

- [ ] Step 1 の提案ファイルに賛否の結論が含まれていない (自己点検)
- [ ] 3 論者全員の結果を受領し、数値照合 (原則 6) を実施した
- [ ] converged / contested を分離して出力した
- [ ] Q ごとの裁定 + 着手条件 + 先にやるべき打ち手を出力した
- [ ] 発見事項を発見メモ queue に記録した
- [ ] Step 5 の routing を実施 (設計書起票 / Issue 追記 / 取り直し優先 のいずれか)

## 由来

ローカル AI プラットフォーム開発 repo で 2026-09-17 に「長時間推論の速度低下対策として、定期的に構造化チェック
ポイントを保存しコンテキストを完全クリアして新セッションで再開する」案を 3 論者で議論した実例から抽出。
そこでは ①③ が既存実装済み・② は過去に有害と判定され除去済み・速度の一次要因は文脈長でなくハードウェア要因、
と判明し「速度対策としては不採用、既存 compaction のチューニング候補へ」と裁定した。同時に「同一タグの再実行で
証跡が上書きされ、2 論者が同一ファイルから別の数値を引用した」事故を原則 6 として取り込んだ。
