# 顧客対応チャットボット運用設計

お客様と直接対話するチャットボットの運用設計書を作る。観点の SoT は `review-chatbot-operation-design` skill の [criteria/chatbot-operation.json](../review-chatbot-operation-design/criteria/chatbot-operation.json)（観点ごとに Anthropic 公式資料の出典か、公式根拠の無い運用慣行であることを明示）。設計書の章立てはその criteria に 1 対 1 で対応させ、完成後はそのままレビューにかけられるようにする。本文に観点の説明を重複して書かない。`review-chatbot-operation-design` skill が無い環境では、下記の章立てを最低限の観点として使う。

## 手順

1. **聞き取り**（`AskUserQuestion` が使えればそれで、無ければ質問を箇条書きで提示する）
   - 対象業務と扱う問い合わせの種類（多い順に 5 件程度）、扱わない話題
   - チャネル（Web チャット・アプリ・メッセージングサービス等）と対応言語
   - 有人体制: 営業時間、担当者の人数、引き継ぎ先（チャット・電話・問い合わせ票）
   - ボットに実行させたい操作（照会・予約・取り消し・返金など）と、その権限の範囲
   - 参照させる情報源（FAQ・規約・商品情報・顧客データ）と、その更新頻度・責任者
   - 既に決まっている KPI や法的な制約
2. **観点の読込**: criteria JSON（上記リンク）を Read し、全 criteria と checks を把握する。`provenance` が `practice` の check は「公式根拠なし（運用慣行）」として扱い、採否を聞き取り結果に合わせて判断する（採らない場合は設計書に理由を書く。レビューでは理由付きの不採用は該当なしとして扱われる。official / official-derived の観点は採らないと不合格の原因になる）
3. **設計書の作成**: 下記の章立てで Markdown を書く。聞き取りで分からない値は推測で埋めず `> [要確認]` と書く
4. **レビューへの接続**: 完成したら `review-chatbot-operation-design` skill でレビューする（自己レビューで完了扱いにしない）

## 設計書の章立て（criteria の id と対応）

1. 対応範囲とタスク（`scope_and_tasks`）: 任せる範囲と理由、理想の対話の流れ（実際の文言で）、タスク分解、範囲外の話題への応じ方、対応言語
2. 回答の根拠（`grounding`）: 参照させる情報源、「分からない」と言ってよい指示、出典の示し方、ナレッジの更新手順と責任者
3. 有人への引き継ぎ条件（`escalation`）: 条件ごとに「検知の方法」と「その時の応答」を表にする
   - お客様のフラストレーション・感情の悪化（何をもって兆候とするか: 否定的な感情が続く・悪化する、同じ質問の繰り返し、強い言葉など。判定方法も書く）
   - 「人と話したい」と言われた時
   - 解決できないやり取りが続いた時（回数を決める）
   - 自信が無い・範囲外の時
   - 権限外の約束・手続きを求められた時
   - 高リスクの話題（苦情・法的・安全・解約など）
4. 引き継ぎの手順（`handoff_protocol`）: 担当者へ渡す要約の項目、お客様への伝え方（待ち時間・次に起きること）、営業時間外・担当者不在時の代替、文脈の保持
5. ガードレール（`guardrails`）: 権限外の約束をしない、個人情報、入力の事前スクリーニング、ツール結果を信頼しない扱い、プロンプト漏洩の監視、口調の一貫性、競合他社への言及の方針
6. ツール連携と操作（`tools_and_actions`）: ツール一覧と権限、影響の大きい操作の前の確認
7. 透明性（`transparency`）: AI であることの伝え方、会話データの扱いの告知
8. 成功基準と評価（`metrics_and_evaluation`）: 品質指標と事業指標を目標値つきで、評価ケース（引き継ぐべき会話と引き継ぐべきでない会話の両方を含む）
9. 運用監視と改善（`monitoring`）: 出力の定期分析、規約を繰り返し破るユーザーへの対応、引き継いだ会話・引き継ぎ漏れの見直し、プロンプトの定期監査
10. 障害時の縮退（`resilience`）: ボット・API 障害時の切り替え先
11. 付録: システムプロンプトの骨子 — 役割、前提知識（ナレッジの差し込み位置）、良い対話例 4〜5 件（引き継ぎとガードレールの例を含む）、ガードレール、引き継ぎ条件

## Examples

- 「EC サイトの問い合わせボットを設計したい」→ 聞き取りで「返品・配送状況・支払い」が上位と分かれば、配送状況はツールで照会、返金は権限外として引き継ぎ条件に入れる
- 聞き取りで有人体制が平日日中のみ → 引き継ぎ手順に「時間外は問い合わせ票を作り、翌営業日に連絡する旨を伝える」を書く
