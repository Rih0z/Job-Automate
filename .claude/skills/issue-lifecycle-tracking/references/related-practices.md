# issue 管理と組み合わせる運用

SKILL.md の起票・遷移・close の手順とは別の、issue の起票につながる運用の決まり。使う repo だけが読む。

## 数値目標は 1 か所に置く

レビューの合格点・カバレッジ目標・スコアの閾値など、頻繁に変わる数値は本体のルール文書に埋め込まず、専用のファイル（例: `issues/records/thresholds.md`、著者の運用例は `state/thresholds.md`）に置き、本体からはリンクだけを置く。

理由: 数値だけが変わるたびに本体の diff が膨らみ、「基準値の更新」と「ルールの構造の変更」が同じ diff に混ざって履歴を追いにくくなる。実コードのカバレッジ % を持たない repo でも、合格率や品質スコアなどの似た閾値に読み替えて当てる。

## レビューが同じ対象で続けて FAIL した時は起票する

レビューのゲートが同じ対象で決まった回数（既定 3 回。repo で別の値を決めていればその値）続けて FAIL したら、修正と再レビューを繰り返さず、作業を止めて `issues/open/` に起票する。本文には、各回でどの評価軸が低かったか・試した内容・残った課題・推奨する次の一手を書く。基準が厳しすぎる、観点がずれている、といった可能性を人が判断する機会を作るため。

文体のレビューが、事実の主張の多い文書で収束しないことがある。その時は文書を直し続けず、文体の採点と事実の突き合わせを別のレビューに分ける。
