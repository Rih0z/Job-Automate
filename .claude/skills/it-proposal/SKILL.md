# 体験価値重視のIT系システム開発ビジネス企画書作成

## 前提

- 必要なツール: ファイルの Read(テンプレート読込)と、保存先指定時の Write。
- `references/proposal-template.md` と `references/self-diagnosis.md` が同じ skill ディレクトリにあること。読めない場合は、第 1〜13 章と付録 A〜E の章立てを本文の出力形式に従って自前で組み、「テンプレート未読込」と冒頭に明記する。
- この skill は SKILL.md と references/ の 2 ファイルだけで動く。元プロンプトの要点（体験価値中心の記述ルール、6 つの自己診断、第 1〜13 章と付録 A〜E の章立て）は本文と references/ に取り込み済み。出元 repo 固有の参照は元プロンプトのパス `workflows/business-planning/it-proposal.md` だけで、無い環境では参照しなくてよい（代替は不要。要点は本文と references/ に取り込み済み）。
- 比較対象に使う他の skill（`review-proposal` など）が無い環境では、次ステップの品質レビューは、同じ観点（手順 4 の (a)〜(d)）をユーザーに確認してもらう形で代える。

## 手順

1. **入力の確認**: 下の「入力情報」10 項目のうち必須（1〜8）を確認する。欠けている項目は、ユーザーに聞き返す。聞き返せない場合に限り、仮置きした内容に「（仮置き）」と明記して進める。9・10 は任意。
2. **体験価値の自己診断**: 下の 6 つの質問に、入力情報だけを根拠に各 1〜3 文で答える。答えられない質問は、手順 1 に戻って該当項目を聞き返す。診断結果は企画書の第 1 章の下書きにする。
3. **企画書の生成**: `references/proposal-template.md` の構造どおりに、全セクションを埋めて Markdown で出力する。技術や機能は体験価値を実現する手段として書く（末尾の記述ルールに従う）。
4. **自己検証**: 出力前に、(a) テンプレートの全見出しが埋まっている、(b) 未入力のまま残った角括弧がない、(c) 数値・競合評価に出典か「仮置き」ラベルがある、(d) 「避けるべき表現」を使っていない、を確認する。満たさない箇所は直してから出力する。
5. **保存と次ステップ**: ユーザーが保存先を指定した場合はそのパスに書く。指定がなければ会話に出力するだけにする。品質レビューは `review-proposal` skill に回す。
6. **完了判定**: 手順 4 の (a)〜(d) が全て満たされ、出力が第 1〜13 章と付録 A〜E を備えた時点で完了とする。

## エラー時の対処

| 状況 | 対処 |
|---|---|
| 必須項目(1〜8)が足りない | 不足項目を箇条書きで聞き返す。聞き返せなければ「（仮置き）」と明記して進める |
| テンプレートや自己診断の references が読めない | 前提のとおり章立てを自前で組み、冒頭に「テンプレート未読込」と書く |
| 市場規模・競合評価などの出典が取れない | 数値を創作せず「仮置き（根拠なし）」と書き、資料の提供を促す |
| ユーザーが数値(予算・目標値)を持たない | レンジと前提条件で示すか「未定」と書く。任意項目 9・10 は空でもよい |
| 入力どうしが食い違う | どちらを採るか聞き返す。聞き返せなければ両方を併記し、冒頭に「入力間の食い違いあり」と明記する |
| 企画書の採点・レビューを頼まれた | この skill では扱わず、`review-proposal` を案内する |

## 使用例

- 依頼: 「習慣化アプリの企画書を体験価値重視で書いて。ターゲットは 30 代の会社員」。入力情報の 3〜8 が不足しているので、手順 1 で不足項目を箇条書きで聞き返す。回答後に手順 2 以降へ進む。
- 依頼: 「入力は全部そろえた。競合の数字はこちらにない」。競合の評価・市場規模は、出典がなければ「仮置き（根拠なし）」と明記して書き、資料の追加を促す。数値を創作して断定しない。
- 依頼: 「この企画書を採点して」。この skill では扱わない。`review-proposal` を案内する。
- 依頼: 「体験価値は『朝の不安が減る』、継続性の欄は『一度使えば課題が完結するので再利用は想定しない』で書いて」。体験価値は日々の継続利用で成り立つのに、継続性の欄が一度きりの利用を前提にしており、入力どうしが食い違う。どちらを採るかをユーザーに聞き返す。聞き返せなければ両方を併記し、「入力間の食い違いあり」と冒頭に明記する。
- 依頼: 「競合と価格を比べて『うちは安い』と書いて」。価格が出典付きで渡されていれば価格帯の比較表にして書く。金額が無ければ「安い」とは書かず、「仮置き（根拠なし）」の行にして金額の提供を促す。

## 根拠と数値の扱い

- 市場規模、成長率、競合の評価（星評価・各種比較表）、収益予測、リテンション目標は、入力または提示資料に出典がある値だけを事実として書く。出典がない値は「仮置き（根拠なし）」と明記するか、レンジと前提条件で示す。
- 実測していない検証結果を「検証済み」と書かない。「計画値」「未検証」と書く。
- 実在の競合名を挙げる場合は、ユーザーが提示した範囲に限る。

## 体験価値の自己診断

手順 2 で、次の 6 つの質問に各 1〜3 文で答える。質問の全文、具体例、よくある間違いは [references/self-diagnosis.md](references/self-diagnosis.md) にある。

| # | 観点 | 答える内容 |
|---|---|---|
| 1 | 本質的な体験価値 | 技術・機能ではなく、ユーザーが得る感情的な体験は何か |
| 2 | 価値の妥当性 | その体験に対価を払う人がいるか、人生にどんな変化があるか |
| 3 | 希少性と必要性 | 既存の方法で簡単に得られないか、どのくらい求められているか |
| 4 | 継続性 | 一度きりでなく、質を保ち続ける仕組みは何か |
| 5 | 習慣化と離脱防止 | 利用頻度、使うほど増す価値、乗り換えで失うもの |
| 6 | 競合への勝ち筋 | 競合の限界と、自社だけの独占的要素は何か |

## 入力情報

必須（1〜8）と任意（9・10）。

1. **企画タイトル**: 製品・サービス名
2. **組織名**
3. **作成者名とポジション**
4. **本質的な体験価値**: ユーザーが得られる感情的・心理的な体験の詳細
5. **体験価値の希少性**: なぜその体験が価値があり、希少なのか
6. **ターゲット市場**: その体験価値を強く求めている具体的な人々
7. **体験価値を支える技術**: 体験価値を実現するための技術やアプローチ
8. **体験価値の継続性**: どのように継続的に体験価値を提供し続けるか
9. **予算範囲（任意）**
10. **実装タイムライン（任意）**

## 出力形式

`references/proposal-template.md` に従う完全な企画書（Markdown、エグゼクティブサマリー、第 1〜13 章、付録 A〜E）。**すべてのセクションで「体験価値」を中心とした記述**を行う。

## 重要な指針

### 体験価値重視の記述ルール

1. **すべての説明は体験価値から始める**
   - 技術説明→体験価値説明 ×
   - 体験価値説明→技術説明 ○

2. **感情的・心理的な影響を具体的に記述**
   - 「効率が向上する」×
   - 「『今日は成果が出そう』という期待感で一日が始まる」○

3. **体験価値の希少性を常に強調**
   - なぜその体験が貴重なのか
   - 他では得られない理由

4. **継続性のある体験価値設計**
   - 一度きりの体験ではなく、継続的に提供できる体験価値

5. **体験価値の測定可能性**
   - 感情的な体験をどのように定量化するか

### 避けるべき表現

次の表現は、体験の中身を示さない主張として単独では使わない。

- 「機能が充実している」
- 「技術的に優れている」
- 「効率的である」
- 「コストが安い」

価格・コストの扱い（テンプレートの比較表との整合）:

- 競合との価格比較表は、テンプレートが要求する項目なので省かない。ただし書くのは、提示価格・価格帯・料金体系といった客観的な事実に限り、出典を添える。出典がなければ「仮置き（根拠なし）」と書く。
- 「安い」「高い」「コスパが良い」は印象評価なので書かない。価格に触れるときは「月額 X 円、競合 A は月額 Y 円（出典）」の形にし、その価格で得られる体験価値と結びつけて述べる。

### 推奨表現

- 「〜という体験を提供する」
- 「〜を実感できる」
- 「〜という希望を与える」
- 「〜という感情を継続的に提供する」
