# モデル選択・委任コスト最適化

プロジェクトの CLAUDE.md・ルール・Skills・カスタムエージェント設定を確認し、モデル振り分け方針（司令塔が難易度・影響範囲・リスク・コストを判断し、定型作業は低コストモデル、複雑な作業は高コストモデルへ委任する）に揃える。対象はすべての業務（実装、調査、障害解析、サポート、資料作成、レビュー等）に汎用で使える運用ルールとする。

## 前提

- 使うツール: Read / Glob(対象ファイルの確認)、Edit / Write(更新を指示された場合のみ)。
- 方針の詳細（第1〜9節）は [references/routing-policy.md](references/routing-policy.md) にある。本文の「第N節」はその節を指す。
- `.claude/agents/` などのパスは Claude Code の標準構成を想定する。サブエージェントの仕組みが無い環境(他のツール等)では、同じ役割分担を CLAUDE.md 相当のルールファイルに文章で書く形で代えてよい。ファイルの場所が分からなければユーザーに確認する。
- この skill は SKILL.md と references/routing-policy.md だけで動く。末尾に挙げる出元 repo の元プロンプトは、この repo 固有で参照しなくてよい。
- 「司令塔 / 低コスト / 高コスト」は役割名。具体的なモデル名（Sonnet / Opus 等）を使うプロジェクトでは置き換えて適用してよい。

## 方針の要点

- 簡単で定型的な実行は低コストモデルへ、複雑で高度な判断を伴う実行は高コストモデルへ委任する。高コストモデルは、低コストで不十分な理由を示せる場合だけ使う。
- 司令塔は全体方針、複数ファイルや複数 Skills に影響する変更、顧客・セキュリティ影響が大きい判断を担い、実行作業を抱え込まない。
- 低コストモデルは、判断困難・設計変更・セキュリティや NDA の懸念・複数ファイル間の矛盾・顧客影響が出たら司令塔へ戻す。

## 進め方（手順とゲート）

1. **確認**（第2節）: 対象ファイルを Read / Glob で確認し、既存のモデル振り分けルールの有無を記録する。
2. **更新の範囲を決める**: ユーザーが「更新して」と明示した、または CLAUDE.md を編集してよいと指示した場合は、実際に更新する。「案を出して」「確認して」の場合、または指示が曖昧な場合は、更新案（差分）を示すだけで、ファイルは変更しない。迷ったら更新案にとどめる。
3. **反映と更新**（第3〜8節）: CLAUDE.md、カスタムエージェント、Skills の順に、方針と矛盾する箇所を直す。CLAUDE.md、skills、agents の変更は、第4節の「司令塔が担当するタスク」に当たるため、**変更の実施と採否は司令塔が自分で行う**。低コスト・高コストに委任してよいのは、現状の調査、整合の確認、修正案の作成までで、ファイルへの反映は司令塔が行う（本 skill の唯一の規則。下の閾値表と判定例、第5・6節も同じ）。
4. **検証**: 下の「完了の判定」を満たすか確認する。満たさない項目が残るときは、完了と報告せず、未達の項目を列挙する。
5. **報告**: 下の「報告形式」で報告する。

### 完了の判定

次の 4 点をすべて満たしたとき完了とする。

- CLAUDE.md（またはそれに相当するルールファイル）に、第3節の項目が書かれている（無い項目は「該当なし」と理由を残す）。
- 司令塔 / 低コスト / 高コストの委任基準が、CLAUDE.md、`.claude/agents/`、関連 Skills の間で矛盾していない（矛盾の有無を、該当箇所の `ファイル名:行番号` つきで確認した）。
- 第6節の「高コストモデルを使う場合に明確にする 5 項目」が、委任指示のテンプレートに入っている。
- 変更したファイルと、変更しなかったファイルの一覧を報告した。

### 振り分けの判定例

- 「誤字と表記ゆれの修正」: 低コスト。判断が不要で、失敗しても影響が小さい。
- 「3 つの skill にまたがる再設計」: skill の変更なので、方針の決定と反映は司令塔(閾値表の行 1)。複数ファイルの整合の調査と案の作成だけを高コストに委任してよい(委任先は行 4 で選ぶ)。
- 「顧客向け回答の下書き」: 下書きは低コスト。社外に出す最終確認は高コスト、または司令塔。
- 「低コストか高コストか判断できない」: 次の閾値表で決める。
- 「委任先のエージェントが失敗した」: 同じ指示で再実行せず、司令塔が失敗の原因を確認する。指示が曖昧なら指示を直し、判断が難しい内容なら、より高い能力のモデルに移す理由を書いてから委任する。

### 低コスト / 高コストの判定閾値

この表は本 skill の既定値。プロジェクトに別の閾値が既にあれば、それを優先する。上から順に見て、最初に当てはまった行で決める。行 1 は変更の実施と採否の担当を決める行で、セキュリティ・NDA・顧客影響が絡んでも行 1 が先に当たる。行 2 以降は、行 1 の対象でない作業と、行 1 の作業のうち調査・案の作成だけを委任するときの委任先の選び方を決める。

| 順 | 条件 | 割り当て |
|---|---|---|
| 1 | CLAUDE.md・Skills・エージェント定義の変更(件数・範囲・セキュリティ等の絡みによらず、実施と採否は常に司令塔) | 変更の実施と採否は司令塔が自分で担当。調査と案の作成だけは委任でき、その委任先は行 2〜6 の条件で選ぶ |
| 2 | セキュリティ・NDA・顧客への影響のいずれかがある | 司令塔が自分で担当、または高コスト(理由を示す) |
| 3 | 社外に出る成果物の最終確認 | 高コスト、または司令塔 |
| 4 | 行 1 以外で、変更・確認の対象が 4 ファイル以上、または 2 つ以上の Skill / ルールにまたがる整合が要る | 高コスト(方針は司令塔が先に決める) |
| 5 | 対象が 1〜3 ファイルで、社外に出ず、手順が決まっている(誤字修正、要約、表記ゆれ、定型変換、初期ドラフト) | 低コスト |
| 6 | 上のどれにも当てはまらない | 低コストで始める |

低コストで始めたあとに、次のいずれかが出たら司令塔に戻す: 判断の分かれる論点が 1 つでも出た、対象が 4 ファイル以上に増えた、同じ指示で 2 回続けて期待と違う結果になった。「4 ファイル」「2 回」は目安の既定値で、プロジェクトで変える場合は CLAUDE.md に書く。

### 使用例

- 依頼: 「このリポジトリのモデル運用ルールを整理して」。第2節の対象を確認し、既存のルールが無ければ CLAUDE.md への追記案を示す。ユーザーが承認した後に更新する。
- 依頼: 「コストを抑えたいので Sonnet でできることは Sonnet に回して」。CLAUDE.md の低コスト向けタスク例と、`.claude/agents/` の executor に当たる定義を確認し、不足していれば追記案を出す。
- 依頼: 「CLAUDE.md と agents の記述が食い違っていないか見て」。両方を読み、矛盾があれば報告表の「見つけた矛盾・不足」に記入し、ファイルは変更しない(更新の明示が無いため)。報告表の記入例:

| 項目 | 内容 |
|---|---|
| 確認した対象 | CLAUDE.md、.claude/agents/executor.md |
| 既存ルールの有無 | あり(CLAUDE.md) |
| 見つけた矛盾・不足 | CLAUDE.md:12 は「定型作業は低コスト」、executor.md:5 は「全作業を担当」と記載 |
| 変更したファイル | 変更なし(更新案のみ) |
| 未達の項目 | 第6節の 5 項目が委任テンプレートに無い |

- 依頼: 「`.claude/agents/` が無いプロジェクトで振り分けルールを作って」。「エラー時の対処」に従い、構成案(CLAUDE.md への追記案とエージェント定義の雛形)だけを示し、ファイルは了承後に作る。

### 報告形式

| 項目 | 内容 |
|---|---|
| 確認した対象 | 読んだファイルのパス |
| 既存ルールの有無 | あり(パス) / なし |
| 見つけた矛盾・不足 | `ファイル名:行番号` と内容 |
| 変更したファイル | パスと変更の要点(更新案のみの場合は「変更なし」) |
| 未達の項目 | 完了の判定のうち満たせなかったもの |

## エラー時の対処

- `.claude/agents/` や `.claude/skills/` が存在しない: 無いことを報告に書き、必要なファイル構成案を示す。ファイルは、ユーザーの了承を得てから作る。
- CLAUDE.md が存在しない: 新規作成の案だけを示して止める。
- ルール同士が矛盾していて、どちらが正しいか判断できない: 変更せず、矛盾の箇所を示してユーザーに確認する。
