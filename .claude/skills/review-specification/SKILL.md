# /review-specification — 技術仕様書 品質レビュー（エージェント分離実行）

> **このスキルは別エージェントを起動してレビューを行う。現在のセッションでは直接レビューしない。**
> 作成時の思考過程・設計判断・会話履歴をレビューエージェントに渡さないことで客観性を確保する。

対象: `specification` skill をもとに生成された技術仕様書
前提: `.claude/agents/readonly-reviewer.md` と `.claude/skills/_shared/review-rubrics.yaml` は Job-Automate repo の固有ファイルで、あればそれを使う。無い環境では `references/reviewer-fallback.md`（審査エージェントの条件・共通原則・判定帯・重大度の定義）で代替でき、SKILL.md と references/ だけで動く。
目的: 「要件の網羅性・正確性」「アーキテクチャ・技術選定の妥当性」「API・データ設計の品質」「テスト・品質保証戦略」「実装計画・運用設計」の5軸で技術仕様書を100点満点で評価する。

---

## 実行手順

### ステップ1: 情報収集（この実装セッションで行う）

以下の事実情報のみを収集する。作成の意図・設計判断の説明は**含めない**。

```
収集対象:
1. レビュー対象の技術仕様書の全文
2. 以下の「レビュー前の必須確認事項」（直下の箇条書き 5 項目）が文書内または作成者からの回答で判明しているか
   - 元となった企画書はどれか
   - 対象システムの規模感は（個人開発・スタートアップMVP・エンタープライズのいずれか）
   - 想定ユーザー数・トラフィック規模は
   - 開発チームの体制・スキルセットは
   - `specification` skill のどのセクションまで記載したか
```

上記が不明瞭な場合は、レビュー開始前に作成者へ確認すること。確認できない項目は「不明」と明記したままレビューを続行してよい（対象文書が技術仕様書でない場合は、実行せずその旨をユーザーに伝える）。

### 使用例

- 「`docs/spec.md` をレビューして」 → ステップ1で全文と確認事項を収集 → ステップ2で readonly-reviewer を起動 → 5軸の採点表と S/A/B/C/D 判定をそのまま表示
- 元企画書が不明な仕様書 → 基本情報の「元企画書」を「不明」とし、要件の網羅性は仕様書内の記述の範囲で採点させる
- 「仕様書を書いて」 → このスキルの対象外。`specification` を案内する
- Agent の起動に失敗した場合 → `readonly-reviewer` が無ければ `general-purpose` で 1 回再試行する。それでも起動できなければ「レビュー未実施」と報告し、現セッションで代わりにレビューしない（詳細は「エラー時の対処」）

### ステップ2: レビューエージェント起動

**Agent ツール**を使い、以下の設定で別エージェントを起動する:

```
Agent ツールの設定:
- subagent_type: "readonly-reviewer"（`.claude/agents/readonly-reviewer.md`。書き込み系ツールを持たない。定義が無い環境・新設直後で未読込のセッションでは "general-purpose" で起動し、prompt 冒頭に「ファイルを作成・変更・削除しない」と明記する）
- description: "Review technical specification objectively"
- prompt: 以下のテンプレートに収集した情報を埋め込む
```

**プロンプトテンプレート（レビューエージェントに渡す内容）:**

`.claude/skills/_shared/review-rubrics.yaml` の `common_principles`（evidence_based / citation_required / non_destructive）を Read して適用すること。

## レビュー観点（5項目・各20点・合計100点）

詳細なチェック項目と採点目安は `.claude/skills/review-specification/references/review-criteria.md` にある。これを Read し、全項目を省略せずに適用すること。読めない場合はその旨を結果の「補足コメント」に書き、5項目の名称（1. 要件の網羅性・正確性 / 2. アーキテクチャ・技術選定の妥当性 / 3. API・データ設計の品質 / 4. テスト・品質保証戦略 / 5. 実装計画・運用設計）と各20点の配点だけで採点して「詳細基準未参照」と明記する。

## 採点方法（総合点：100点満点）

`.claude/skills/_shared/review-rubrics.yaml` を Read し、`verdict_scales.rank5_100` の bands/meaning に従って S/A/B/C/D を判定すること（点数帯・各段階の対応方針は同ファイルが SoT。同ファイルが無い場合は `.claude/skills/review-specification/references/reviewer-fallback.md` の判定帯・共通原則・重大度を適用する）。**指摘単位の重大度**: 各観点の個別指摘には同ファイルの `severity` (HIGH/MEDIUM/LOW) を付し、出力の「具体的な強化が必要な箇所」表の「重大度」列に書く（総合点の算出方法は変更しない）。

### ステップ3: 結果の報告

レビューエージェントから返却された結果を、そのままユーザーに表示する。

### エラー時の対処

| 状況 | 対処 |
|------|------|
| 対象文書のパスが無い・読めない | 実行せず、対象ファイルの絶対パス（または全文）の提示をユーザーに求める |
| `.claude/skills/_shared/review-rubrics.yaml` が読めない | レビューエージェントには、読めなかった旨を伝え、本テンプレート内の採点目安のみで採点させる（判定 S/A/B/C/D の帯は報告時に「rubrics 未参照」と明記） |
| Agent の起動に失敗した | `readonly-reviewer` が無ければ `general-purpose` で再試行。それでも起動できなければレビューは未実施とし、現セッションで代替レビューはしない |
| 返却結果が出力フォーマットに沿わない | 同じ入力でレビューエージェントを 1 回だけ再起動し、フォーマット遵守を明記する。なお崩れる場合は返却内容をそのまま表示し、崩れている旨を添える |

## 注意事項

- **絶対に実装セッション内で直接レビューしない**。必ず Agent ツールで別エージェントを起動すること
- レビュワーは元ファイルを絶対に編集してはならない。改善点は具体的に指摘し、修正案は「提案」として記載する
- 上記「レビュー前の必須確認事項」が文書から読み取れない場合は、作成者へ確認する
