# 盲検一括評価ハーネス

## 概要

「AIが複数のサンプルに対してタスクを実行し、その結果を別のAIまたは人間が採点する」形式のテストで、**採点担当がサンプルの正体・カテゴリを推測できてしまうと盲検が崩れる**問題を構造的に防ぐ。カテゴリ名を含むフォルダ名・過去run結果・正解データへの参照経路を、削除運用ではなく**構造(新規dir + allow-list)**で塞ぐ。

対象: 複数サンプルの一括精度検証(単発の1ケース評価には使わない — 単発は各領域の通常タスクとしてそのまま実行する)。

## Phase 1: test-ready 点検

実行前に以下を確認し、不足があれば起動せず報告する:
- 評価対象サンプル一式が実在するか(`ls` / Glob で実在確認。2 件未満なら本 skill の対象外)
- 各サンプルの期待結果(ground truth)が別途 SoT として存在するか(採点担当には渡さない)
- 実行担当・採点担当それぞれの手順(SoT skill/prompt)が存在するか

不足の報告様式: 「不足項目 / 確認したパス / 必要な対応」を 1 行ずつ列挙し、全て解消されるまで Phase 2 に進まない。

**run-id の形式**: `YYYYMMDD-HHMMSS`(例 `20260901-143005`)。同名 dir が既にあれば秒を進めて再生成し、上書きしない。

## Phase 2: 盲検実行の起動(別エージェント)

**盲検の担保は構造で行う(手動の削除運用に依存しない)**:

1. **run dir の新規作成(パス再利用禁止)**: run開始時にタイムスタンプ付き新規dir(例 `.tmp/eval_run/{run-id}/`。配置先がこの repo の規約と異なる環境では、その環境の一時作業領域に同じ構造で作る)を作成し、サンプルコピー・作業ファイルは全てこの配下に置く。前回runと同じパスを使い回さない。
2. **読取 allow-list(禁止リストの反転)**: 実行担当への dispatch prompt には「Read してよいのは①自分のrun dir配下 ②渡されたサンプルコピー ③一般的な手順・ナレッジ資料のみ」と allow-list 形式で明記する。ground truth・過去run結果・カテゴリ別フォルダなど漏洩経路になり得るパスは、禁止リストとして列挙する(=漏れがある)のではなく、そもそも許可リストに入れない(=列挙漏れごと塞ぐ)。
3. **中立名でのコピー**: サンプルは元のカテゴリ名・案件名が推測できるパス/ファイル名のまま渡さず、`sample_1`, `sample_2` のような中立名でrun dir配下にコピーしてから実行担当へ渡す。
4. 実行担当は**別エージェント**として起動し、渡すのは中立名のサンプルパスのみ(会話履歴・意図・カテゴリ情報は渡さない)。
5. **旧run dirは削除しない**(比較・再検証・証跡保持のため)。盲検の有効性は新規dir+allow-listの構造で担保済みであり、旧dirを残しても汚染しない。

## Phase 3: 採点への dispatch(実行担当とは別エージェント)

採点担当も別エージェントで起動し、渡すのは①実行担当の出力パス ②対応する ground truth パスの2点のみ。sample_N と元サンプルの対応は、dispatch する親（呼び出し側）だけが run dir 外の対応表（採点完了までは採点担当・実行担当に見せない）で保持し、そこから各 sample の ground truth パスを引いて渡す。実行担当が辿った試行錯誤・中間判断は渡さない(結果のみで公平に採点させる)。

## Phase 4: 記録

- 各サンプルの採点結果・合否を run dir 配下の `results.md` に次の表で記録する(sample_N と元サンプルの対応表は、採点完了後にのみ別ファイル `mapping.md` へ書く)。

| sample | 実行出力パス | ground truth パス | 採点(点/判定) | 合否 | 根拠(採点担当が引用した出力のパス・行) |
|---|---|---|---|---|---|

- 合否の基準は、依頼元の採点 skill / prompt が定める閾値に従う。基準が示されていなければ記録せず依頼元に確認する(本 skill が閾値を決めない)。
- 閾値未達の原因切り分け(ハーネス側の欠陥かサンプル側の問題か)は本skillの対象外— 結果を元の依頼者へ返す。

## 使用例

ユーザー: 「この 8 件のログに対する AI 解析を盲検で一括評価して」
→ Phase 1 で 8 件と ground truth の実在を確認 → `.tmp/eval_run/20260901-143005/` を作成し `sample_1`〜`sample_8` にコピー → 実行担当を別エージェントで起動 → 各出力を採点担当へ(出力パスと ground truth パスのみ)→ `results.md` に 8 行の表を記録して依頼元へ返す。

## エラー時の対処

- **実行担当・採点担当エージェントが失敗/タイムアウト**: 該当 sample のみ同じ run dir で 1 回だけ再実行する。再失敗なら表に「実行不能」と理由を書き、他 sample の結果は有効のまま返す。run dir を作り直して全体をやり直す場合は新しい run-id を使う。
- **サンプル数が 2 件未満/ground truth が一部欠落**: 欠落 sample を除外して続行せず、Phase 1 の様式で報告して起動を止める。
- **採点担当が採点不能と返した**: 理由を原文で記録し、点数を推測で補わない。
- **中立名コピーでもファイル内容にカテゴリ名が含まれる**: コピー前に気付いたら依頼元へ報告する(内容の書き換えは本 skill の範囲外)。

## 落とし穴

- **フォルダ名に「test」「eval」を含むが実際は単発1件の依頼**: 依頼が「1件を評価してレポートを書くだけ」であれば、フォルダ名に関わらず本skillは使わず、通常のタスクとしてそのまま実行する(誤起動によるトークン浪費を防ぐ)。
- **run dir を使い回すと過去の中間ファイルが残り、次のサンプルのヒントになり得る**: 必ず新規dirを切る。
