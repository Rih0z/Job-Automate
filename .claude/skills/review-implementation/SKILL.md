# /review-implementation — 実装品質 総合レビュー

> プロジェクト全体の実装品質を5軸（テスト・正確性・マネタイズ・ペルソナ・UX）で100点満点評価する。
> 評価軸・採点表・出力フォーマットは `references/` に分離している（下記「参照ファイル」）。

> **このコマンドは別エージェントを起動してレビューを行う。現在のセッションでは直接レビューしない。**
> 実装コンテキスト（思考過程・設計判断・会話履歴）をレビューエージェントに渡さないことで客観性を確保する。

## 前提と環境依存

- **収集パスは固定の配置が前提**: ステップ1 の収集パス（`workflows/software-development/...`）と `.claude/agents/readonly-reviewer.md` は Job-Automate リポジトリ固有の配置。他のプロジェクトでは、まずステップ1 の「代替」に従い **Glob で探し**、見つからない項目は **「未検出」と記録して進め（停止しない）**、エージェントは `general-purpose` で代替する。
- 必要なツール: Read / Glob / Grep（収集）、Agent（レビュー起動）。ファイルの編集・コマンド実行はしない。
- 評価軸・判定表・出力フォーマットは SKILL.md 単体でなく `references/` が正本。コピー時は `references/` ごと移す。

## 実行手順

### ステップ1: 情報収集（この実装セッションで行う）

以下の事実情報のみを収集する。実装の意図・目的・設計判断の説明は**含めない**。

```
収集対象:
1. ペルソナ定義: workflows/software-development/design/persona.md
   （なければ「未検出」と記録するのみ。推定ユーザーの創作・注記はここでは行わない）
2. 収益モデル: README 等に記載の内容（なければ「未検出」と記録）
3. テスト戦略: jest.config.* / vitest.config.* / pytest.ini 等のテスト設定ファイルの検出と内容
4. デザインガイドライン: workflows/software-development/design/design-guidelines.md
   （なければ「未検出」と記録）
5. コーディング規約: workflows/software-development/rules/coding-principles.md
   （なければ「未検出」と記録。レビューエージェントは一般的な規約で評価し、その旨を注記する）
6. プロジェクトの実装成果物一覧（対象ディレクトリのファイル構成・主要ソースファイル）
7. workflows/software-development/review-implementation.md の内容
   （評価基準の詳細チェックリスト — プロジェクト内にあれば読み込む）
```

**収集パスが固定の配置と違う場合の代替:** 上記パスに無いときは、Glob で `**/persona*`・`**/design-guideline*`・`**/coding*`・`**/review-implementation*` を探し、見つかった最初の候補を使う（候補が複数ならパスを併記して全て渡す）。それでも無ければ「未検出」と記録する。成果物一覧の対象が不明なときは、引数で渡されたディレクトリを使い、引数も無ければ、リポジトリ直下の主要ソースディレクトリ（`src/`・`app/`・`lib/` 等で実在するもの）に絞り、どれを対象にしたかを結果に書く。

**収集の原則:**
- 収集するのは事実情報（設定ファイルの中身・ファイル一覧・ドキュメントの記載内容）のみ
- 実装の意図・設計判断の解説・会話履歴の要約はここに含めない
- 各項目が未検出の場合は「未検出」とだけ記録し、代替の推定・仮定はステップ1では行わない
  （代替方針の適用はステップ2のレビューエージェント側の判断に委ねる）

### ステップ2: レビューエージェント起動

**Agent ツール**を使い、以下の設定で別エージェントを起動する:

```
Agent ツールの設定:
- subagent_type: "readonly-reviewer"（`.claude/agents/readonly-reviewer.md`。書き込み系ツールを持たない。定義が無い環境・新設直後で未読込のセッションでは "general-purpose" で起動し、prompt 冒頭に「ファイルを作成・変更・削除しない」と明記する）
- description: "Review implementation quality objectively"
- prompt: 以下のテンプレートに収集した情報を埋め込む
```

**プロンプトテンプレート（レビューエージェントに渡す内容）:** 下の「そのまま埋め込む」指示では、先に `references/rubric.md` と `references/output-format.md` を Read して本文を取得する。

```
あなたはシニアアーキテクト兼品質保証エキスパートです。
実装者とは別の客観的な立場から、プロジェクトの実装成果物を5軸（テスト・正確性・マネタイズ・ペルソナ・UX）で
100点満点評価してください。

## 行動原則
- 証拠主義: コードの事実のみに基づいて評価する。推測でスコアを付けない
- 各スコアにはファイルパスと行番号の引用を最低1つ以上含め、減点理由には該当行の短い引用を添えること。引用できない指摘は出さない
- 非破壊: レビューのみ行い、コードの編集・実行は行わない
- 証拠不十分時は、該当する軸の採点目安（references/rubric.md「2. 軸ごとの採点目安」）のうち、証拠で裏づけられた最も低いレンジの下限で採点する
```

## Examples

- ユーザー: 「プロジェクト全体をレビューして」→ `/review-implementation` を実行 → ペルソナ定義・収益モデル・テスト戦略等を収集（未検出は「未検出」と記録） → 別エージェントを起動 → 5軸スコアと判定（S〜D）を表示。
- ペルソナ定義が無いプロジェクト → 推定ユーザーを仮定した上でその旨をレポートに明記して評価を継続する（N/A 除外はしない）。
- 収益モデルが無いプロジェクト → マネタイズ軸を N/A として除外し、残り4軸・80点満点を 合計点 ÷ 80 × 100 で換算する（例: 4軸合計 68点 → 85点 → 判定 A）。

- エージェントが失敗・空応答を返した場合 → 結果を補完せず、同じプロンプトで 1 回だけ再起動する。再度失敗したら「レビュー失敗」とその返却内容をそのまま報告する（点数を推測で埋めない）。
- 対象ディレクトリが存在しない・空の場合 → エージェントを起動せず、対象のパスをユーザーに確認する。

## 対象範囲（`review-changes` との違い）

本スキルは**プロジェクト全体の実装成果物**を評価する（マネタイズ・ペルソナ・UX 軸を含む）。直近の変更差分だけを評価したい場合は `/review-changes` を使う。

## 注意事項

- **絶対に実装セッション内で直接レビューしない**。必ず Agent ツールで別エージェントを起動すること
- レビューエージェントに渡す情報は事実（設定ファイルの中身・ファイル一覧・ドキュメントの記載内容）のみ。実装の意図・設計判断・会話履歴は渡さない
- 対象範囲が小さい場合でも分離実行する。規模で判断しない
