# 審査ルーブリック（4基準・判定規則・共通原則・重大度）

SKILL.md と `criteria/oss-contribution.json` だけで審査を完結させるための要点。`.claude/skills/_shared/review-rubrics.yaml`（Job-Automate repo 固有）がある環境では、そちらの `verdict_scales.go3` と `severity` が正本。この文書はその要点の写しで、食い違ったら repo 側を優先する。

## 4基準

各基準を ✅（クリア）/ △（軽微な懸念）/ ❌（重大な懸念）で判定する。チェック項目の正本は `criteria/oss-contribution.json`。

| 基準 | 見ること |
|---|---|
| 独自性（最重要） | 自プロジェクト独自の知見か。他 OSS 由来ならライセンス互換性を確認済みか。再配布・改変が認められないソース（非公開コードのリーク、閲覧のみ許諾のソース等）由来の設計パターンでないか |
| 先行技術 | 同じアプローチが既に提案されていないか。マージ済みの修正で解決済みでないか。活発な議論が進行中で割り込む余地がないか |
| 実現可能性 | PR が小規模（初回貢献の目安は +50 行以内）か。対象 OSS の言語で実装できるか。CI/テストを通せるか |
| 戦略 | Issue と最小 PR を同時に出す計画か。Issue で手の内を見せすぎていないか。PR が 1 目的に絞られているか |

## 総合判定の規則（優先順位の高い順）

1. 独自性が ❌ → 他基準によらず **REJECT**（倫理・ライセンスリスクのため最優先）。
2. 独自性が ✅ で、残り 3 基準のいずれかが ❌ → **REJECT**（例: 同一アプローチがマージ済み、対象 OSS の言語で実装不可、Issue で手の内を見せすぎ）。
3. 独自性が ✅ で、❌ は無く 1 つ以上 △ → **HOLD**（懸念を解消して再提出）。
4. 独自性が ✅ で、残り 3 基準が全て ✅ → **GO**。

△ の例: PR がやや大きい、先行議論はあるが方向性が異なる、Issue 先出しの順序が最適でない。

## 汚染検知 grep

プロジェクト内に参照禁止のソース（非再配布・流出ソース）のディレクトリがある場合だけ、候補の記述にあるクラス名・関数名・変数名をそのディレクトリに Grep し、一致を確認する。該当ディレクトリが無い環境では N/A と書く。

## 共通原則（common_principles の要点）

- 証拠主義: 推測で判定しない。候補ファイルの記載だけで評価する。記載が足りない基準は、記載不足を理由に △ 以下とする。
- 引用義務: 各基準の判定に、候補ファイルの該当箇所を逐語引用で添える（ファイル名と行番号つき。行番号が分からない場合は節見出し名）。
- 非破壊: 審査のみ行い、候補ファイルを編集しない。修正案は「提案」として書く。

## 指摘単位の重大度（severity の要点）

❌ と △ の理由には、1 件ごとに重大度を付ける。総合判定の規則は変えない。

| 重大度 | 定義 | 対応 |
|---|---|---|
| HIGH | 内容の正確性・実行可能性を損なう重大な欠陥 | 修正必須（次工程へ進めない） |
| MEDIUM | 品質を下げるが致命的ではない欠陥 | 次イテレーションで修正 |
| LOW | 軽微な改善余地 | 推奨（任意） |

## 審査エージェントの条件（readonly-reviewer の代替）

- `.claude/agents/readonly-reviewer.md` が無い環境では、Agent ツールに `general-purpose` を指定し、prompt 冒頭に「ファイルを作成・変更・削除しない」と明記する。
- Bash を使う場合は読み取りと検査に限る。結果はファイルに書かず応答本文で返す。
- 実装意図や会話履歴は渡さない。基準に無い好みの指摘は optional として分け、基準違反だけを blocking にする。
