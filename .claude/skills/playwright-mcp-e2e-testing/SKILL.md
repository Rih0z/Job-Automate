# Playwright MCP による E2E テスト

## 前提条件と必要入力

- 必要な環境: Node.js と npm(`npx` で `@playwright/mcp` を起動する)、プロジェクトルートに `.mcp.json` を置ける Claude Code 環境。
- 使うツール: Playwright MCP の `browser_*` ツール、`.mcp.json` の編集用 Read / Edit。
- この skill は SKILL.md と references/report-template.md だけで動く。末尾の出典に挙げる `workflows/...` は出元 repo 固有のパスで、無い環境では参照しなくてよい。
- description が「使わない場面」で挙げる他の skill(`single-session-tdd`、`three-agent-tdd-workflow`、`review-changes`、`mcp-server-setup`)は、この skill には含まれない。環境に無い場合は、案内先として名前を出さず、「単体テストやコードレビューはこの skill の対象外」とだけ伝え、ユーザーの手元の手段(テストランナーや通常のレビュー)に任せる。MCP の導入は、下の「セットアップ」の手順で足りる範囲だけ行う。

テストを始める前に、次の入力をユーザーから受け取る。欠けているものは推測せず質問する。

- 対象 URL（ローカル開発サーバーまたはステージング）。**本番環境には実行しない**。
- テスト対象の機能・画面の一覧（例: ログイン、一覧、フォーム送信）。
- 認証が必要な場合のテスト用アカウント（本番アカウントや実在ユーザーの情報は使わない）。
- バックエンド/API テストを行う場合は API のベース URL とテスト用データの扱い（作成したデータを消してよいか）。

## セットアップ

プロジェクトルートの `.mcp.json` に以下を記載する（既存の `mcpServers` がある場合は `playwright` エントリだけ追記し、他の設定を消さない）。`@latest` は常に最新を取得するため、再現性が要るときは `@playwright/mcp@<確認済みのバージョン>` に固定する。

```json
{
  "mcpServers": {
    "playwright": {
      "command": "npx",
      "args": [
        "@playwright/mcp@latest"
      ]
    }
  }
}
```

### 接続確認（テスト開始前のゲート）

1. Claude Code を再起動するか MCP を再読込し、`browser_navigate` などの `browser_*` ツールが使えることを確認する。
2. 対象 URL を `browser_navigate` で開き、`browser_snapshot` でページ内容が取れれば準備完了。

失敗時の対処:

- `browser_*` ツールが見えない: `.mcp.json` の JSON 構文と配置場所を確認し、再起動する。
- `npx` が起動しない: Node.js と npm が入っているか（`node --version`）を確認する。Windows では環境変数 PATH の反映に再起動が要ることがある。
- ブラウザが無いというエラー: `browser_install` ツールでブラウザを導入する。
- 対象 URL に接続できない: 開発サーバーの起動状況とポートを確認し、起動できなければ該当テストを「未実施（環境不備）」として報告する。

## テスト実行方針

- **アプローチ**: Bottom-up（単体→統合→システム）と Top-down（ユーザー視点→技術詳細）の両方。
- **品質観点**: 機能性、性能、セキュリティ、ユーザビリティ、保守性。
- 「ユーザーが実際に使うシナリオ」を最優先に設計し、証拠（スクリーンショット）は「スクリーンショット取得ルール」の必須タイミングで残す。

### 使うツール

コードを書くのではなく、Playwright MCP のツールを呼び出して操作する。

| 目的 | ツール |
|---|---|
| ページ遷移 | `browser_navigate` |
| ページ構造の取得 | `browser_snapshot` |
| スクリーンショット | `browser_take_screenshot` |
| クリック・入力・フォーム | `browser_click` / `browser_type` / `browser_fill_form` |
| 画面サイズ変更 | `browser_resize` |
| コンソールエラー | `browser_console_messages` |
| 通信内容（API のステータス・応答） | `browser_network_requests` |
| 時間やメモリなどの計測 | `browser_evaluate` |

## 合否判定の基準

各テストは次の基準で PASS / FAIL / 未実施を付ける。

- **PASS**: 期待する表示・遷移・ステータスコードが得られ、コンソールにエラーがない。
- **FAIL**: 期待と異なる結果、コンソールエラー、HTTP 4xx/5xx（異常系テストで意図したものを除く）。実際の値と期待値を記録する。
- **未実施**: 前提（環境・権限・対象機能の有無）が満たせず実行できなかった。理由を書く。
- 性能は、ユーザーが基準を指定した場合のみ数値で判定する。指定がなければ測定値を記録するだけにして、合否は付けない。

## テスト項目

実行する項目の選び方:

- ユーザーが範囲を指定した場合(画面名、機能名、項目番号)は、その項目だけを実行する。
- 指定が無く「E2E テストして」だけの場合は、対象の機能一覧(前提条件で受け取ったもの)に関係する項目を選ぶ。UI が無ければ 1〜5 を外す。バックエンドだけの場合は、下の「項目ごとの実行可否」で「実行可能」「条件付き」の項目から選び、「実行手段なし」の項目(部分)は選ばずに「未実施（環境）」と報告する。
- 全 19 項目の一括実行は、ユーザーが「全部」「網羅的に」と明示した場合だけ行う。
- 選ばなかった項目は、レポートに「対象外」と項目番号の一覧で書く(範囲指定の場合も同じ)。「対象外」は PASS / FAIL / 未実施の件数に含めない。

### 項目ごとの実行可否(`browser_*` ツールだけで実行できるか)

- **実行可能**: `browser_*` ツールだけで実行できる。
- **条件付き**: 画面操作を介する、または `browser_evaluate` で対象ページから呼び出せる範囲に限り実行できる。その範囲を超える部分は「未実施（環境）」とする。
- **実行手段なし**: `browser_*` ツールでは実行できない。選ばず、「未実施（環境）」と理由を報告する。

| 項目 | 実行可否 |
|---|---|
| 1〜4, 9, 11, 12, 17 | 実行可能 |
| 5 | 条件付き(ブラウザを切り替えられる場合のみ。手順は項目 5) |
| 6〜8 | 条件付き(画面操作で発生する通信を `browser_network_requests` で確認、または `browser_evaluate` からの呼び出しに限る) |
| 10, 14, 16, 18, 19 | 条件付き(画面や通信から観察できる範囲に限る) |
| 13 の平均レスポンス時間 | 条件付き(`browser_evaluate` で計測できる範囲に限る) |
| 13 の同時接続数・スループット | 実行手段なし |
| 15 の SQL インジェクション | 実行手段なし |
| 15 の認証強度・データ暗号化 | 条件付き(画面や通信から観察できる範囲に限る) |

### 1. フロントエンド

1. **ページロード**: 初期表示のスクリーンショット、ロード時間、コンソールエラーを確認する。
2. **レスポンシブ**: `browser_resize` でデスクトップ（1920x1080）、タブレット（768x1024）、モバイル（375x667）に切り替え、各サイズでスクリーンショットを取る。
3. **基本操作**: クリック、入力、スクロール。各操作後にスクリーンショットを取り、アニメーション・トランジションも確認する。
4. **フォーム**: 正常値、必須入力・形式のバリデーション、エラーメッセージ表示。送信前後でスクリーンショットを取る。
5. **ブラウザ互換性**: Chrome、Firefox、Safari、Edge の主要機能。既定のブラウザ以外に切り替える手順は次のとおり。
   1. 切替に使えるオプションを確認する。`npx @playwright/mcp@latest --help` を実行し、出力に `--browser` があるかを見る。無ければ切替はできないので、この入れ子の最後の番号（切り替えられない場合の扱い）に進む。
   2. `.mcp.json` の `playwright` の `args` に、`--browser` と対象ブラウザ名を追記する。例: `["@playwright/mcp@latest", "--browser", "firefox"]`。指定できるブラウザ名は手順 1 の `--help` の出力に載っている語だけを使う(Chrome、Firefox、Safari に当たる名前が載っているか確認し、載っていない名前は指定しない)。
   3. Claude Code を再起動するか MCP を再読込し、`browser_install` でそのブラウザを導入する。
   4. 「接続確認」と同じく `browser_navigate` → `browser_snapshot` で開けるかを確かめる。開ければ、そのブラウザで項目 1〜4 を再実行する。
   5. 切り替えられない、または導入できないブラウザは「未実施（環境）」とし、理由(`--help` に無かった、導入に失敗した等)を書く。Safari は macOS 以外で動かせないことがあるため、同様に扱う。
   ブラウザごとの結果は、レポートのエビデンスでブラウザ名が分かるようにファイル名の「操作内容」に含める(例: `login_firefox_submit_...png`)。

### 2. バックエンド

6. **REST API**: GET/POST/PUT/DELETE の動作、ステータスコード、レスポンスデータ、レスポンスタイム。
7. **認証・認可**: ログイン/ログアウト、権限チェック、セッション管理。
8. **CRUD とデータ整合性**: データの作成・読み取り・更新・削除、トランザクション整合性、データ型・制約。テストで作ったデータは、ユーザーの了承があれば後始末する。

### 3. 統合

9. **エンドツーエンドシナリオ**: ユーザージャーニー全体を通し、各ステップでスクリーンショットを取りデータフローを確認する。
10. **リアルタイム機能**（該当する場合）: WebSocket 通信、リアルタイム更新、通信状態変化時の表示。

### 4. パフォーマンス

11. **ページロード**: FCP / LCP / CLS（`browser_evaluate` で Performance API から取得する）。
12. **JavaScript 実行性能**: 重い処理の実行時間、メモリ使用量。
13. **API 性能**: 各 API の平均レスポンス時間、同時接続数、スループット。負荷をかけるテストは、ユーザーが対象環境と上限を了承した場合のみ行う。

### 5. セキュリティ

14. **フロントエンド**: XSS 対策、CSRF 対策、入力値サニタイズ。
15. **バックエンド**: SQL インジェクション対策、認証強度、データ暗号化。

セキュリティテストの制約:

- 自分が管理するテスト環境、または所有者の書面による許可がある環境だけで行う。許可の有無が不明なら実施せず、ユーザーに確認する。
- 本番環境や第三者のサービスへは行わない。
- 実在の個人情報や認証情報を使わない。データ破壊や大量リクエストを伴う手法は、ユーザーが明示的に了承しない限り行わない。

### 6. エラーハンドリング

16. **異常系**: ネットワークエラー、サーバーエラー時の挙動。各エラー状態でスクリーンショットを取る。
17. **境界値**: 入力値の上限・下限、エッジケース。

### 7. 関連機能

18. **依存機能**: メール送信、ファイルアップロード、外部 API 連携。動作時のスクリーンショットを取る。
19. **通知**: プッシュ通知、画面内通知。表示時のスクリーンショットを取る。

実際に存在しない機能（例: WebSocket を使わないアプリのリアルタイム機能）は「未実施（対象機能なし）」とする。

## スクリーンショット取得ルール

### 取得タイミング

1. **必須**: 初期ページロード後、主要操作の前後、エラー発生時、テスト完了時。
2. **詳細**: フォーム入力中・入力後、モーダル・ポップアップ表示時、データ更新前後、レスポンシブ表示切り替え時。

### ファイル命名規則

```
{テスト項目}_{操作内容}_{日時}.png
例: login_form_input_20261030_143022.png
```

`{日時}` は実行したマシンのローカル時刻を `YYYYMMDD_HHMMSS`(秒単位、24 時間表記)で書く。タイムゾーンは記録しない。同じ秒に同名ができた場合は末尾に `_2` を付ける。

保存先はプロジェクト内の作業用ディレクトリ（例: `.tmp/e2e-screenshots/`）とし、ユーザーに伝える。機密画面（個人情報が写るもの）はコミットしない。

## テスト結果レポート

最終応答に次の 3 つを、この順で含める。表のひな形は [references/report-template.md](references/report-template.md)。

1. **実行結果サマリー**: PASS / FAIL / 未実施の件数、主なバグ・課題、パフォーマンス指標。
2. **詳細テスト結果**: 各テスト項目の結果、スクリーンショット（ファイル名）付きのエビデンス、改善提案。
3. **次回テスト時の改善点**: テストケース見直し、自動化範囲の拡張、継続監視ポイント。

## 使用例

```
ユーザー: 「http://localhost:3000 のログイン画面を E2E テストして」
→ 必要入力を確認（テスト用アカウント、対象は開発環境）
→ 接続確認: browser_navigate → browser_snapshot
→ 項目 1〜4, 7, 16 を実行: 3 サイズのスクリーンショット、正常/不正入力でのログイン、エラー表示
→ 結果: login_*.png の一覧と、実行 6 項目の内訳(PASS 4 / FAIL 1 / 未実施 1)のサマリー。選ばなかった項目 5〜6、8〜15、17〜19 は「対象外」と番号で一覧する
```

- 依頼: 「API の一覧取得だけ確認して」。項目 6 のみを実行し、`browser_network_requests` でステータスとレスポンスを確認する。他の項目(1〜5、7〜19)は「未実施」ではなく「対象外」として、番号の一覧だけをレポートに載せる。UI が無く、`browser_evaluate` からも呼び出せず `browser_*` で確認できない API は、上の実行可否表に従い「未実施(環境)」と報告する。
